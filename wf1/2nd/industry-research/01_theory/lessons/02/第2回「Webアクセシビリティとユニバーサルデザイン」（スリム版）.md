# 第2回「Webアクセシビリティとユニバーサルデザイン」（10/20）

# **1. Webアクセシビリティ・ユニバーサルデザインの基本理念**

## **1-1. Webアクセシビリティ（Web Accessibility）とは**

### **【アクセシビリティの定義と対象】**

高齢者や障害のある人を含め、すべての人が心身の条件や利用環境（デバイス、OS、通信速度、周囲の状況等）に関わらず、Webで提供されている情報や機能にアクセスし、問題なく利用できること。

特定の障害者だけのものではなく、一時的な怪我（片手しか使えない）や状況的な制約（日差しの強い屋外、音が出せない環境）など、**「すべての利用者に役立つWebサイトの基本的品質」**です。

### **【アクセシビリティとユーザビリティの違い】**

| 概念 | 定義・内容 |
| --- | --- |
| **アクセシビリティ<br>（Accessibility）** | 多様な利用者が、どんな環境からでも情報や機能に「到達・知覚・操作できるか」 |
| **ユーザビリティ<br>（Usability）** | 特定の利用状況において、特定のユーザーが目標を達成する際の「有効さ・効率・満足度」 |

<aside>
💡

**両者の関係**

アクセシビリティが担保されていなければ、そもそも利用すらできないため、ユーザビリティを論じることができません。

</aside>

---

## **1-2. ユニバーサルデザイン（Universal Design）とバリアフリー**

### **【ユニバーサルデザイン（UD）の定義】**

1980年代に米国の建築家ロナルド・メイス（Ronald Mace）氏が提唱した概念。**「年齢、性別、能力、状況の違いに関わらず、最初からできるだけ多くの人々が利用できるように製品や環境をデザインすること」**を指します。

※ 障害者や高齢者だけを対象に限定したものではありません。

### **【バリアフリーとの違い】**

| 概念 | 主な対象 | アプローチ・考え方 |
| --- | --- | --- |
| **バリアフリー** | 障害者や高齢者 | すでに存在する「**障壁（バリア）を後から取り除く**」事後対応 |
| **ユニバーサルデザイン** | すべての人 | 「**最初からバリアが生じないように設計する**」事前設計 |

### **【ユニバーサルデザインの7原則】**

1. **公平な利用：** だれでも同じように利用できること（差別や孤立を生じさせない）。
2. **利用における柔軟性：** 個人の好みや能力に合わせて使い方を選べること（右利き・左利きの両対応など）。
3. **単純で直感的な利用：** 経験、知識、言語能力に関係なく直感的に使えること。
4. **認知できる情報：** 必要な情報が使い手に効果的に伝わること（視覚・聴覚・触覚などの併用）。
5. **エラーへの寛容性：** 間違った操作をしても危険や重大な損害に至らないこと（元に戻す機能など）。
6. **少ない身体的努力：** 無理な姿勢をとらず、疲れにくいこと。
7. **接近して利用するためのサイズと空間：** どんな体格や姿勢でも操作しやすいスペースがあること。

# **2. 多様な利用者の特性と配慮**

## **2-1. 障害特性とWeb閲覧時の配慮**

まずは、多様な障害特性を持つ利用者がWeb閲覧時に直面する困難を理解することが重要です。

| 障害特性 | 直面する困難・利用する支援技術 | 求められるWeb上の配慮 |
| --- | --- | --- |
| **視覚障害<br>（全盲）** | 画面の視覚情報が見えないため、**スクリーンリーダー**（音声読み上げ）や点字ディスプレイに依存する。 | 正しい見出し構造（`h1`〜`h6`）をマークアップし、画像には的確な `alt` 属性を提供する。 |
| **視覚障害<br>（ロービジョン/弱視）** | 小さな文字や薄い色のコントラストが判別しにくい。画面拡大機能を使用する。 | 文字を拡大しても文字の重なりや横スクロールが発生しないレスポンシブな設計にする。 |
| **聴覚障害<br>（ろう・難聴）** | 音声情報が聞こえないため、動画のセリフや通知音が伝わらない。 | 動画に**キャプション（字幕）**や全文文字起こし（トランスクリプト）を用意する。 |
| **肢体不自由<br>（上肢障害）** | マウスの精密なポインティングやドラッグ操作が困難。キーボードやスイッチ入力を使用。 | すべてのリンクやボタンが**キーボードのみで操作可能**であること。 |
| **認知・発達障害** | 複雑な文章の理解、時間制限、予測不能な画面変化に強いストレスを受ける。 | 平易な言葉遣い、一貫したレイアウト、入力フォームの制限時間の延長・解除機能を提供する。 |

---

## **2-2. 高齢者・状況的制約への配慮**

加齢に伴い、視力の低下（細かい文字の見えにくさ）、コントラスト感度の低下、細かなマウス操作の困難などが生じます。

<aside>
⚠️

音声読み上げソフトがあるからといって、**画面上の文字拡大機能を制限してはなりません**（高齢者や弱視者は画面拡大を併用します）。

</aside>

# **3. Webアクセシビリティの規格体系と法制度**

## **3-1. 国際規格 WCAG と 日本産業規格 JIS X 8341-3**

Webアクセシビリティには国際的な共通ガイドラインと、それに準拠した日本産業規格が存在します。

![出典：[https://hellouniweb.com/columns/wcag/](https://hellouniweb.com/columns/wcag/)](https://uniweb-service-site-origin.s3.ap-northeast-1.amazonaws.com/contents/2024/10/15162459/WCAG%E3%81%A8ISO%E3%81%8A%E3%82%88%E3%81%B3JIS%E3%81%AE%E9%96%A2%E4%BF%82-768x702.png)

出典：[https://hellouniweb.com/columns/wcag/](https://hellouniweb.com/columns/wcag/)

### **【WCAG（Web Content Accessibility Guidelines）】**

Web標準化団体W3C内の専門部会「WAI（Web Accessibility Initiative）」が策定する国際的なアクセシビリティ指針。

### **【JIS X 8341-3（高齢者・障害者等配慮設計指針）】**

日本の国家規格（Webコンテンツ編）。規格番号「8341」は「やさしい」の語呂合わせに由来。

現行の「JIS X 8341-3:2016」は、国際規格 WCAG 2.0 と同一内容で整合されています。

---

## **3-2. JIS X 8341-3 の4つの原則（POURの原則）**

Webコンテンツが満たすべき4つの基本理念です。各原則の下にガイドラインと達成基準が定められています。

| 原則 | 基本理念と概要 | 代表的なガイドライン・達成基準 |
| --- | --- | --- |
| **知覚可能<br>（Perceivable）** | 情報及びインタフェースは、利用者が知覚できる方法で提示しなければならない。 | ・「**非テキストコンテンツ**」には代替テキストを提供する。<br>・色だけを、情報を伝える「唯一の視覚的手段」としない。<br>・背景と文字の間に十分なコントラスト比を確保する。 |
| **操作可能<br>（Operable）** | インタフェース及びナビゲーションは、操作可能でなければならない。 | ・すべての機能を「**キーボード**」から利用できるようにする。<br>・光の点滅（1秒に3回超）による発作を避ける。<br>・リンクの「**テキスト**」単独でリンク先が判断できるようにする。 |
| **理解可能<br>（Understandable）** | 情報及びユーザインタフェースの操作は、理解可能でなければならない。 | ・ページの言語（**`html lang="ja"`**）をプログラムで判定可能にする。<br>・入力エラー箇所と具体的な修正方法を明示する。 |
| **堅牢<br>（Robust）** | 支援技術を含む多様な環境が確実に解釈できるように堅牢でなければならない。 | ・HTMLの文法仕様（完全な開始・終了タグ、一意なID属性など）に準拠する。 |

---

## **3-3. 適合レベルと法制度**

アクセシビリティの達成度合いを評価する客観的なレベルと法律上の義務です。

### **【適合レベル（達成等級：A / AA / AAA）】**

| 適合レベル | 位置づけ | 概要・説明 |
| --- | --- | --- |
| **レベルA** | 最低限 | すべてのWebサイトが必ず達成すべき最低基準。 |
| **レベルAA** | 推奨水準 | **公的機関や企業の一般的な目標水準**。国際的にもレベルAAへの適合が標準的なゴールとされます。 |
| **レベルAAA** | 最高水準 | 最も高度な基準。全コンテンツでの一律達成は困難とされます。 |

### **【法制度の動向：障害者差別解消法（2024年4月義務化）】**

法改正により、行政機関だけでなく**民間事業者に対しても「合理的配慮の提供」が法的義務化**されました。

Webアクセシビリティの向上は、合理的配慮を的確に行うための環境整備として極めて重要です。

# **4. 視覚・情報伝達のアクセシビリティ設計**

## **4-1. 代替テキスト（img 要素と alt 属性）の鉄則**

`alt` 属性は、**「その画像と同等の情報・役割を伝えるテキスト（代替テキスト）」**です。

画像の見た目を客観描写するものではなく、画像が表示されない環境や支援技術に対して「画像の代わり」として提供します。

| 画像の種類 | `alt` 属性の指定ルール | 具体例 |
| --- | --- | --- |
| **情報伝達画像** | 画像が伝えている情報・内容を記述 | **`<img src="sales.png" alt="2025年度売上推移グラフ：前年比120%増">`** |
| **操作アイコン・ボタン** | 見た目ではなく**機能・目的**を記述 | 虫眼鏡アイコン ➔ **`alt="検索"`**（× **`alt="虫眼鏡"`**）<br>歯車アイコン ➔ **`alt="設定"`**（× **`alt="歯車"`**） |
| **装飾用画像** | **空のalt（`alt=""`）** を指定する | **`<img src="line.png" alt="">`**<br>（空文字は文法エラーではなく、支援技術に読み飛ばさせるための正しい指定） |
| **画像送信ボタン** | **`input type="image"` にも `alt` 属性を指定できる** | **`<input type="image" src="submit.png" alt="送信する">`** |
| **文字画像（バナー等）** | 画像内の文字と**全く同じ文字列**を指定 | **`<img src="campaign.png" alt="夏の特大セール 最大50%OFF">`** |

```html
<!-- ⭕️ 良い例：情報伝達画像 -->
<img src="chart.png" alt="2025年度売上推移グラフ：前年比120%増">

<!-- ⭕️ 良い例：装飾用画像（読み飛ばさせる） -->
<img src="decoration-line.png" alt="">

<!-- ❌ 悪い例：alt属性そのものを省略（ファイル名が読み上げられる） -->
<img src="logo.png">
```

## **4-2. マルチメディアの代替情報**

音声や動画などのマルチメディア情報に等しくアクセスするための代替要件です。

| 代替情報の種類 | 概要・機能 | 主な対象・メリット |
| --- | --- | --- |
| **キャプション<br>（同期字幕）** | 音声情報（セリフ、話者名、効果音、BGMの雰囲気）を動画と同期させて文字表示する機能。 | 聴覚障害者や、音が出せない環境の閲覧者に必須。 |
| **音声解説<br>（オーディオディスクリプション）** | 映像内の視覚情報（登場人物の動き、表情、場面転換、画面上の文字）をセリフの合間に音声で説明する機能。 | 全盲の利用者に必須。 |
| **トランスクリプト<br>（全文テキスト起こし）** | 音声配信やポッドキャストの内容をテキスト化した文書。 | 通信環境の悪い場所や検索性の向上にも役立つ。 |

## **4-3. 色に依存しない情報伝達と視覚コントラスト**

色覚多様性を持つ利用者や明所環境でも情報が正確に伝わるようにするための配慮です。

### **【色だけに頼らない設計】**

「赤色の文字が必須項目」「赤枠の入力欄がエラー」のように色だけで情報を伝えてはなりません。

「【必須】」「※」といったテキストや記号・アイコンを必ず併用します。

![出典：[https://www.tribeck.jp/column/opinion/20260401/](https://www.tribeck.jp/column/opinion/20260401/)](https://www.tribeck.jp/column/assets_c/2026/03/01-thumb-720xauto-17479.png)

出典：[https://www.tribeck.jp/column/opinion/20260401/](https://www.tribeck.jp/column/opinion/20260401/)

### **【コントラスト比の基準（レベルAA）】**

背景色と文字色の間の明るさの比率（コントラスト比）を確保します。

| 条件・文字サイズ | 最低コントラスト比 |
| --- | --- |
| 一般的な本文サイズ | **4.5：1 以上** |
| 18pt以上、または14pt以上の太字 | **3.0：1 以上** |

<aside>
💡

**白背景（`#ffffff`）に黒文字（`#000000`）のコントラスト比は最大（21:1）であり、最も視認性が高く推奨される組み合わせです。**

</aside>

## **4-4. カラーユニバーサルデザイン（CUD）と色覚の多様性**

人間の色覚特性は多様であり、特定の色の組み合わせが見分けにくい利用者が存在します（特に緑の感度が弱い「D型色覚」が先天色覚異常で最多）。

### **【区別がつきにくい色の組み合わせ】**

「赤と緑」「緑と茶色」「紫と青」「ピンクと灰色」など。

![出典：[https://ringochann.jp/](https://ringochann.jp/)](https://ringochann.jp/wp-content/uploads/2024/07/IMG_5387.jpeg.webp)

出典：[https://ringochann.jp/](https://ringochann.jp/)

### **【配慮の実践】**

- 色相（色味）の違いだけでなく、明るさ（明度）の差を大きくして識別しやすくする。
- グラフには模様・網掛け（ハッチング）や数値ラベルなど、色以外の判別要素を併用する。

## **4-5. Webセーフカラー（Web Safe Colors）**

コンピュータの表現色数が少なかった黎明期に定められた歴史的カラーパレットです。

256色環境のモニターでもディザリング（網点処理による濁り）を起こさずに共通して再現できる**「216色」**で構成されています。

![出典：[https://www.selecolor.com/](https://www.selecolor.com/)](https://www.selecolor.com/img/web-safe-color-palette.png)

出典：[https://www.selecolor.com/](https://www.selecolor.com/)

### **【Webセーフカラーの見分け方】**

RGBの各2桁（`RR`, `GG`, `BB`）がすべて **「00, 33, 66, 99, CC, FF」のいずれか** で構成されているかを確認します。

- 例：`#0066CC` ➔ `00`, `66`, `CC` はすべて含まれるため **Webセーフカラーである**。
- 例：`#EEEEEE` や `#FF1493` ➔ `EE` や `14` は含まれないため **Webセーフカラーではない**。

### **【Webセーフカラーの代表的な色一覧】**

| 表示される色 | 16進数カラーコード |
| --- | --- |
| **黒** | **`#000000`** |
| **白** | **`#FFFFFF`** |
| **赤** | **`#FF0000`** |
| **緑** | **`#00FF00`** |
| **青** | **`#0000FF`** |
| **黄** | **`#FFFF00`** |
| **シアン（水色）** | **`#00FFFF`** |
| **マゼンタ（赤紫）** | **`#FF00FF`** |
| **セーフブルー** | **`#0066CC`** |
| **濃いグレー** | **`#666666`** |
| **標準グレー** | **`#999999`** |
| **薄いグレー** | **`#CCCCCC`** |

## **4-6. 文字・フォントとWeb表記の配慮**

弱視者やディスレクシア（読字障害）の利用者にも読みやすい文字表示と、環境による文字化けを防ぐ表記の配慮です。

### **【ユニバーサルデザインフォント（UDフォント）】**

年齢、性別、障害（ロービジョン、ディスレクシア等）の有無にかかわらず、**「できるだけ多くの人が見やすく、読みまちがえにくいように配慮して設計された書体」**。

| 要素 | 具体的な工夫・設計 |
| --- | --- |
| **視認性<br>（見やすさ）** | 文字の輪郭の隙間を広げ、濁点・半濁点（「ば」と「ぱ」など）を大きく強調して判別しやすくしている。 |
| **判読性<br>（誤読防止）** | 形状の似ている文字（「1」「l」「I」や「O」「0」、「ソ」「ン」など）が明確に区別できるようにデザインされている。 |
| **可読性<br>（疲れにくさ）** | 文字の太さをできる限り均一に保ち、画面上で小さく表示しても文字がつぶれたりかすれにくく、長文でも疲れにくい設計。 |

### **【ファイル名・URLにおける全角・機種依存文字の禁止】**

ファイル名やディレクトリ名に「全角文字（日本語）」「スペース」「機種依存文字」を使用してはなりません。

サーバーやブラウザ間での文字コード解釈の不一致により、「文字化け」や「リンク切れ（404 Not Found）」の直接の原因となります。

<aside>
💡

**命名ルール**

半角英小文字（`a-z`）、半角数字（`0-9`）、ハイフン（**`-`**）、アンダースコア（`_`）のみを使用します。

</aside>

### **【機種依存文字（環境依存文字）の問題点】**

丸付き数字（①②）やローマ数字（ⅠⅡ）、単位記号（㌢、㈱）などは、利用者のOS（Windows, Mac, スマートフォン等）やフォント環境によって**文字化け**したり、スクリーンリーダーで正しく読み上げられない（または無音になる）リスクがあるため、Webページの本文やリンクでの使用を避けます。

![出典：[https://spring8.jp/archive/ja/about_us/site_tour/characters/](https://spring8.jp/archive/ja/about_us/site_tour/characters/)](https://spring8.jp/archive/ja/about_us/site_tour/img/characters.png)

出典：[https://spring8.jp/archive/ja/about_us/site_tour/characters/](https://spring8.jp/archive/ja/about_us/site_tour/characters/)

### **【文字実体参照（Character Entity References）】**

HTMLでは `<` や `>` などの記号は「タグの開始・終了」を意味する予約文字であるため、そのまま記述すると文法エラーや表示崩れを引き起こします。

画面上にこれらの特殊記号を安全に表示するために**文字実体参照**を使用します。

| 表示される記号 | 文字実体参照 | 説明 |
| --- | --- | --- |
| **`<`** | **`&lt;`** | **小なり記号（Less Than）** |
| **`>`** | **`&gt;`** | **大なり記号（Greater Than）** |
| **`&`** | **`&amp;`** | **アンパサンド（Ampersand）** |
| **`"`** | **`&quot;`** | **二重引用符（Double Quote）** |
| **`©`** | **`&copy;`** | **著作権記号（Copyright）** |
| （空白） | **`&nbsp;`** | **改行なしスペース（Non-Breaking Space）** |

# **5. 操作性・対話機能の実装とセマンティクス**

## **5-1. スクリーンリーダー（画面音声読み上げソフト）**

スクリーンリーダーは画面の見た目（CSS）ではなく、ブラウザが構築した**HTMLの文書構造**を読み上げます。

### **【代表的なソフトウェア】**

| 利用環境 | 対応OS | 代表的なソフトウェア |
| --- | --- | --- |
| **PC環境** | Windows | ・**NVDA**（無償・オープンソース）<br>・**JAWS**<br>・**PC-Talker** |

### **【マークアップの影響】**

見出し（`h1`〜`h6`）が正しく設定されていれば利用者は見出しジャンプ機能で目的の箇所へ素早く移動できます。

## **5-3. リンク表現と動的コンテンツの配慮**

操作性や認知に関する重要な実装ガイドラインです。

## **5-4. タッチターゲットと入力支援・制限時間**

手や指の動作、認知や集中力に特性を持つ利用者が、ストレスなく安全に操作を完結させるための要件です。

| 配慮項目 | 具体的な要件・配慮内容 |
| --- | --- |
| **十分なタッチターゲット** | モバイル等のボタンは、誤タップを防ぐため十分な大きさ（おおむね **44 × 44px 以上**）と余白を確保する。 |
| **誤操作の防止と確認画面** | 注文や送信などの重要な操作では、送信前の確認画面や、送信直後の取り消し手段を用意する。 |
| **制限時間（タイムアウト）の配慮** | フォーム入力などで時間制限がある場合、制限時間を延長または解除できる機能を提供する。 |
| **入力エラーの修正支援** | 単に「エラーがあります」ではなく、「電話番号はハイフンなしの半角数字で入力してください」のようにエラー箇所と具体的な修正方法を明示する。 |

## **5-5. WAI-ARIAの基本とセマンティクス拡張**

ネイティブHTMLだけでは表現しきれないリッチなWebUI（モーダル、タブ、アコーディオン等）に対し、属性を付加して役割や状態を支援技術に伝えるための標準仕様です。

### **【WAI-ARIAの3大要素（役割・状態・特性）】**

WAI-ARIAは、HTML要素に属性を追加することで、支援技術（スクリーンリーダー等）にUIの「役割」「状態」「特性」を伝達します。

| 区分 | 意味と役割 |
| --- | --- |
| **役割（Role）** | その要素が「**何であるか（UIの種類・機能）**」を定義する。 |
| **状態（State）** | ユーザーの操作によって**動的に変化する「現在の状態」**を伝える。 |
| **特性（Property）** | 要素の「**性質・本質的な特徴**」を伝える（頻繁に変化しない）。 |

### **【ARIAの第1原則（First Rule of ARIA）】**

<aside>

**「ネイティブなHTML要素や属性で実現できるのであれば、ARIAを使ってはならない。」**

</aside>

標準のHTML要素（**`<button>`, `<a>`, `<input>`** 等）には、ブラウザによって最初からキーボード操作（Tab移動、EnterやSpaceでの実行）や読み上げ機能が完全に組み込まれているため、ARIAで擬似的に自作するよりも標準タグを使う方が安全でアクセシブルです。

**例：ボタンの実装（ネイティブタグ vs 自作ARIA）**

```html
<!-- ❌ 悪い例：divタグで作った自作ボタン（キーボード操作やフォーカスが動かない） -->
<div role="button" onclick="submitForm()">送信</div>

<!-- ⭕ 良い例：標準のbuttonタグを使う（追加コードなしでキーボード・支援技術に完全対応） -->
<button type="button" onclick="submitForm()">送信</button>
```

# **1. コンピュータの5大装置とハードウェア基礎**

## **1-1. コンピュータの5大装置とCPUの役割**

コンピュータは、制御・演算・記憶・入力・出力という「5大装置」の連携によって動作します。

### **【コンピュータの5大装置の役割】**

```
                    ［コンピュータの5大装置とデータの流れ］
     ┌───────────┐      制御信号       ┌──────────────────────┐
     │           ├─────────────────>│      制御装置 (CU)     │
     │ 入力装置  │                     ├──────────────────────┤ CPU (中央処理装置)
     │ (キーボード)│      データ入力      │      演算装置 (ALU)    │
     │ (マウス)   ├─────────────────>└──────────┬───────────┘
     └───────────┘                              │ データ受渡
                                                ▼
     ┌───────────┐      データ出力      ┌──────────────────────┐
     │ 出力装置  │<─────────────────┤    主記憶装置 (RAM)   │
     │ (画面・印)│                     └──────────┬───────────┘
     └───────────┘                                │ 読み書き
                                                  ▼
                                       ┌──────────────────────┐
                                       │ 補助記憶装置 (SSD/HDD)│
                                       └──────────────────────┘
```

| 装置分類 | 英語名称 | 主な役割・機能 | 代表的機器・部品 |
| --- | --- | --- | --- |
| **制御装置** | Control Unit (CU) | 命令を解読し、他装置へ指示・制御信号を送る。 | **CPU（中央処理装置）**内部 |
| **演算装置** | Arithmetic Logic Unit (ALU) | 四則演算や論理演算を実行する。 | **CPU（中央処理装置）**内部 |
| **記憶装置** | Memory / Storage | プログラムやデータを一時的・長期的に保管する。 | **主記憶（RAM）**、**補助記憶（SSD/HDD）** |
| **入力装置** | Input Device | 外部からデータや指示を送り込む。 | **キーボード、マウス、タッチパネル** |
| **出力装置** | Output Device | 処理結果を人間に認識できる形で提示する。 | **ディスプレイ、プリンタ、スピーカ** |

> **CPU（Central Processing Unit）：**
> 「制御装置」と「演算装置」を統合したコンピュータの頭脳。性能は**クロック周波数（GHz）**やコア数（マルチコア）で決まります。

## **1-2. メモリとストレージの記憶階層**

記憶階層は、処理速度と容量・コストのバランスを最適化するために多層的に構成されています。

### **【記憶階層の構造（上ほど高速・小容量 / 下ほど低速・大容量）】**

1. **レジスタ：** CPU内部の最速メモリ。
2. **キャッシュメモリ（SRAM）：** CPUと主記憶の間の一時バッファ。
3. **主記憶装置（DRAM / メインメモリ）：** 実行中のOSやプログラムを展開。
4. **補助記憶装置（SSD / NVMe）：** 高速フラッシュメモリ。
5. **補助記憶装置（HDD / 磁気ディスク）：** 大容量の磁気記録ディスク。

### **【主記憶と補助記憶の特徴】**

- **RAM（主記憶）：** 読み書き自由。電源を切るとデータが消える**「揮発性」**。実行中OSやアプリを展開。
- **ROM：** 電源を切ってもデータが保持される**「不揮発性」**。起動用プログラム（BIOS/UEFI）を記録。

| 比較項目 | SSD（Solid State Drive） | HDD（Hard Disk Drive） |
| --- | --- | --- |
| **記憶媒体** | **フラッシュメモリ（電子回路）** | **磁気ディスク（プラッタ）** |
| **駆動部** | **物理的可動部なし（完全無音・耐衝撃性高）** | モーターと磁気ヘッドによる**物理駆動あり（衝撃に弱い）** |
| **読み書き速度** | **極めて高速** | 相対的に低速 |
| **容量単価** | やや高価 | **安価でテラバイト（TB）級の大容量** |

> **周辺インターフェース規格：**
> - **USB Type-C：** 上下対称コネクタ。高速転送、映像出力（Alt Mode）、急速給電（USB PD）に対応。
> - **HDMI / DisplayPort：** 外部ディスプレイへの映像・音声デジタル伝送規格。

## **1-3. OS（基本ソフトウェア）とファイル権限管理**

OS（基本ソフトウェア）は、ハードウェアとアプリケーションの間でシステム全体を管理・制御するソフトウェアです。

### **【OSの基本概念とファイル権限】**

- **Webサーバの代表的OS：** **Linux**（オープンソース・無償・高安定性で世界の大半を占める）、**Windows Server**。
- **OSS（オープンソースソフトウェア）：** ソースコードが無償公開され改変・再配布可能なソフト（Linux, Apache, MySQL, PHP, WordPress等）。
- **ファイルパーミッション：** 各ファイルに「所有者」「グループ」「その他」への**読取（r=4）**・**書込（w=2）**・**実行（x=1）**権限を設定。設定誤りは「**403 Forbidden（アクセス拒否）**」の原因となります。

# **2. サーバ・クライアントシステムと主要ミドルウェア**

## **2-1. システム形態の基本構造**

ネットワークシステム形態は、要求側と提供側を明確に分ける「サーバ・クライアント型」が基本となります。

### **【代表的なシステム形態】**

```
［サーバ・クライアントモデル］
    クライアント（PC / スマホ）                    Webサーバ（クラウド / 物理サーバ）
   ┌──────────────────────┐                      ┌──────────────────────┐
   │ Webブラウザ (Chrome等)│ ── ① HTTPリクエスト ──> │ Webサーバ (Apache等) │
   │                      │ <── ② HTTPレスポンス ── │                      │
   └──────────────────────┘    (HTML/CSS/画像を返却) └──────────────────────┘
```

- **サーバ・クライアント型：** リクエストする側（クライアント）と処理・提供する側（サーバ）を分ける集中型モデル。
- **P2P（Peer to Peer）：** 全端末が対等にデータを送受信し合う分散型モデル（ブロックチェーン等）。

# **3. Webシステムの3層アーキテクチャと信頼性設計**

## **3-1. 3層クライアントサーバシステムの構造**

3層アーキテクチャは、Webシステムをプレゼンテーション層・アプリケーション層・データ層の3つに機能分離する設計モデルです。

### **【Webシステムの3層構造】**

> **［Webシステムの3層アーキテクチャの流れ］**  
> **Webブラウザ**（クライアント） ➔ **Webサーバ**（プレゼンテーション層） ➔ **APサーバ**（アプリケーション層） ➔ **DBサーバ**（データ層）

- **プレゼンテーション層（Webサーバ：Apache / Nginx）：**  
  クライアントからのリクエスト受付、静的ファイル配信、SSL/TLS暗号化の終端を担います。
- **アプリケーション層（APサーバ：PHP / Node.js等）：**  
  業務処理（ビジネスロジック）を実行し、データベースへの問い合わせを行います。
- **データ層（DBサーバ：MySQL / PostgreSQL等）：**  
  データの永続的な保管、高速検索、トランザクション管理を行います。

- **3層構造のメリット：** DBが直接外部ネットワークに晒されないためセキュリティが強固になり、階層ごとに独立して機器の増設（スケールアウト）が可能になります。

---

## **3-2. 静的Webサイト vs 動的Webサイト**

Webサイトの配信方式は、固定のHTMLを返す「静的サイト」と、アクセス時にHTMLを動的生成する「動的サイト」に分かれます。

### **【静的サイトと動的サイトの比較】**

| 比較項目 | 静的Webサイト（HTML） | 動的Webサイト（CMS / Webアプリ） |
| --- | --- | --- |
| **コンテンツ生成** | サーバー上のHTMLファイルをそのまま返却。 | リクエスト時にプログラムが**HTMLを都度自動生成**。 |
| **表示内容** | **いつ、誰が見ても同一内容**。 | ログイン状態や検索条件により**表示内容が変化**。 |
| **代表例** | 会社案内、ポートフォリオ、LP | **WordPress**、ECサイト、SNS |
| **メリット** | サーバ負荷が極小、高速、脆弱性が少ない。 | ブラウザから容易に更新可能、高度な機能を提供。 |
| **WordPress連携** | なし | **PHP（AP機能）**が**MySQL（DB機能）**から記事を取得・結合してHTML出力。 |

## **3-3. システム信頼性指標と稼働率計算**

システムの信頼性設計は、稼働率や平均故障間隔などの定量指標を用いて安定稼働を評価する手法です。

### **【信頼性の主要指標と計算公式】**

- **MTBF（平均故障間隔）：** 故障修理完了から**次の故障までの正常稼働平均時間**（長いほど信頼性が高い）。
- **MTTR（平均修復時間）：** 故障発生から**修理復旧までの平均時間**（短いほど保守性が高い）。

> **稼働率 ＝ MTBF ÷ (MTBF ＋ MTTR)**

### **【実践！稼働率の計算例題】**

> **【例題1：単一サーバの稼働率】**  
> MTBFが **495時間**、MTTRが **5時間** のサーバの稼働率はいくらか。  
> ➔ **稼働率** ＝ 495 ÷ (495 ＋ 5) ＝ 495 ÷ 500 ＝ **0.99（99%）**

> **【例題2：並列冗長化システムの稼働率】**  
> 稼働率 **0.9（90%）** のサーバを2台並列に配置し、1台でも動いていれば継続できるシステムの稼働率はいくらか。  
> 1. 2台同時に故障する確率：(1 − 0.9) × (1 − 0.9) ＝ 0.1 × 0.1 ＝ **0.01**  
> 2. 全体稼働率：1 − 0.01 ＝ **0.99（99%）**

- **拡張方式：**
  - **スケールアップ（垂直拡張）：** 既存サーバ自体のCPUやメモリを増強。
  - **スケールアウト（水平拡張）：** 同等のサーバ台数を増やしてロードバランサで負荷分散（クラウドの標準）。

# **4. リレーショナルデータベース（RDB）とACID特性**

## **4-1. RDBの基本概念（テーブル・レコード・カラム）**

リレーショナルデータベース（RDB）は、すべてのデータを2次元の「表（テーブル）」形式で関係付けて管理するシステムです。

### **【RDBのデータ構造】**

| user_id（カラム） | name（カラム） | email（カラム） | role（カラム） |
| :---: | :---: | :---: | :---: |
| 1 | 山田太郎 | yamada@example.com | admin |
| 2 | 佐藤花子 | sato@example.com | member |

- **テーブル（表）：** 関連データの入れ物。
- **レコード（行 / タプル）：** データ1件分の水平方向の集まり（例: 山田太郎さんのデータ1行分）。
- **カラム（列 / フィールド / 属性）：** 項目名を表す垂直方向の並び（データ型を規定）。

---

## **4-2. キーの概念（主キーと外部キー）**

データベースのキーは、レコードを一意に特定し、複数テーブル間の関連付けを正しく保つための識別情報です。

### **【主キーと外部キーの役割】**

- **主キー（Primary Key：PK）：**  
  テーブル内の**各レコードを一意（ユニーク）に識別する列**。
  - **一意性制約：** 値の重複不可。
  - **非NULL制約：** 値が空（NULL）であってはならない。
- **外部キー（Foreign Key：FK）：**  
  別テーブルの主キーを参照する列。
  - **参照整合性制約：** 参照先（親テーブル）に存在しないIDは登録できない。

> **［主キーと外部キーのリレーション例］**  
> **注文テーブル（orders）** の `user_id`（外部キー） ── 参照 ──> **会員テーブル（users）** の `user_id`（主キー）

---

## **4-3. データの正規化と関係演算**

データ設計と抽出処理は、データの重複を排除する「正規化」と、必要な情報を自在に引き出す「関係演算」によって行われます。

### **【データの正規化（重複排除と矛盾防止）】**
- **第1正規化：** 繰り返し項目を排除し、各マスを単一値（原子値）にする。
- **第2正規化：** 主キーの一部に従属する項目を分離（部分関数従属の排除）。
- **第3正規化：** 主キー以外の項目に従属する項目を分離（推移的関数従属の排除）。

### **【3大関係演算】**
- **選択（Selection）：** 条件に合致する「**行**」を抽出（SQLの`WHERE`）。
- **射影（Projection）：** 必要な「**列**」のみを抽出（SQLの`SELECT`）。
- **結合（Join）：** 共通のキーで複数テーブルを合体（SQLの`JOIN`）。

---

## **4-4. トランザクション処理とACID特性**

トランザクション処理は、複数の処理を分離できない「1つの処理単位」として実行し、データの整合性を厳格に保証する仕組みです。

### **【トランザクションが満たすべきACID特性】**

| 特性 | 英語名称 | 保証される動作 |
| --- | --- | --- |
| **原子性** | **Atomicity** | 全て実行されるか、全く実行されないかのどちらか（**All or Nothing**）。障害時は**ロールバック（巻き戻し）**。 |
| **一貫性** | **Consistency** | 処理前後でデータベースの制約・整合性が常に保たれる。 |
| **独立性** | **Isolation** | 同時実行されても、互いの途中経過に影響を与えず順番に実行された結果と一致する。 |
| **耐久性** | **Durability** | 一度完了（**コミット**）した結果は、その後の障害や停電でも永久に失われない。 |

- **排他制御（ロック）：** 同時更新時の矛盾を防ぐ施策。互いのロック解除を待ち合って停止する現象を**デッドロック**と呼ぶ。
- **RDB vs NoSQL：** 厳密な整合性・決済を重視する「RDB（MySQL）」に対し、超高速読み書き・柔軟性を重視する「NoSQL（Redis, MongoDB）」。

# **5. SQL入門とデータベースセキュリティ**

## **5-1. データ操作言語（DML）とトランザクション制御**

SQLは、リレーショナルデータベースに対してデータの検索・追加・更新・削除を指示するための標準言語です。

### **【主要なDML命令（データ操作言語）】**

| 命令文 | 役割・構文 |
| --- | --- |
| **`SELECT`** | データ検索・抽出：`SELECT カラム FROM テーブル WHERE 条件;` |
| **`INSERT`** | 新規レコード挿入：`INSERT INTO テーブル (列1, 列2) VALUES (値1, 値2);` |
| **`UPDATE`** | レコード更新：`UPDATE テーブル SET 列 = 値 WHERE 条件;` |
| **`DELETE`** | レコード削除：`DELETE FROM テーブル WHERE 条件;` |

- **トランザクション制御（TCL）：** `START TRANSACTION`（開始）➔ `COMMIT`（確定反映）/ `ROLLBACK`（取り消し）。

---

## **5-2. SELECT文の句とセキュリティ**

SELECT文は、複数の句を組み合わせて柔軟なデータ抽出を行う命令であり、安全な実行のためのセキュリティ対策が不可欠です。

### **【SELECT文の基本構文と主要句】**

```sql
SELECT title, price, category
FROM products
WHERE price >= 1000 AND category = 'Web書籍'
ORDER BY price DESC
LIMIT 10;
```

- **主要句のルール：**
  - `FROM`：対象テーブル
  - `WHERE`：抽出条件（比較演算子、`AND`/`OR`、部分一致 `LIKE '%Web%'`）
  - `ORDER BY`：並び順（`ASC` 昇順 / `DESC` 降順）
  - `LIMIT`：取得上限件数
  - `INNER JOIN`：外部キーによるテーブル結合
  - `GROUP BY`：集計関数（`COUNT`, `SUM`, `AVG`）によるグループ別集計

### **【データベースのセキュリティ対策】**
- **SQLインジェクション防止：**  
  入力フォームに不正なSQL文を注入される攻撃。防ぐためには**プレースホルダ（バインド機構）**を用いて入力値を純粋なパラメータとしてエスケープ処理することが必須です。

# **6. クラウドコンピューティングと仮想化技術**

## **6-1. クラウドのサービス形態（SaaS・PaaS・IaaS）**

クラウドサービスは、事業者が提供する管理レイヤーの違いによってSaaS・PaaS・IaaSの3つに分類されます。

### **【サービスモデル別の責任分界点】**

| 管理レイヤー | オンプレミス | IaaS | PaaS | SaaS |
| --- | :---: | :---: | :---: | :---: |
| **アプリケーション** | 自社管理 | 自社管理 | 自社管理 | **事業者提供** |
| **データ** | 自社管理 | 自社管理 | 自社管理 | **事業者提供** |
| **ランタイム** | 自社管理 | 自社管理 | **事業者提供** | **事業者提供** |
| **OS** | 自社管理 | 自社管理 | **事業者提供** | **事業者提供** |
| **仮想化基盤** | 自社管理 | **事業者提供** | **事業者提供** | **事業者提供** |
| **物理インフラ** | 自社管理 | **事業者提供** | **事業者提供** | **事業者提供** |

### **【SaaS・PaaS・IaaSの概要と代表例】**

| 形態 | 略称・提供範囲 | 代表例 |
| --- | --- | --- |
| **SaaS** | ソフトウェア・アプリケーション機能そのものを提供。即利用可能。 | **Google Workspace, Notion, Figma** |
| **PaaS** | アプリ実行基盤（OS、DB、言語環境）を提供。開発者はコード開発に専念。 | **AWS Elastic Beanstalk, Heroku** |
| **IaaS** | 仮想サーバ、ストレージ、ネットワーク等のインフラ基盤を提供。自由度最高。 | **AWS EC2, Google Compute Engine** |

---

## **6-2. 仮想化とコンテナ技術**

仮想化技術は、1台の物理サーバー上で複数の独立した実行環境を効率的に稼働させるインフラ技術です。

### **【仮想化方式の種類と特徴】**

- **ハイパーバイザー型仮想化：** ハードウェア上に直接仮想化OS（VMware等）を導入し高速動作。クラウドの基盤。
- **コンテナ型仮想化（Docker）：** ホストOSのカーネルを共有し、アプリ実行環境を「コンテナ」として軽量・高速に分離。開発環境の統一に不可欠。
- **サーバレス（FaaS）：** サーバを常時待機させず、リクエスト発生時にのみ関数コードを実行して課金される形態（AWS Lambda等）。

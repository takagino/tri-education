# 3. なぜ「px」だけではいけないのか？（絶対単位の限界とアクセシビリティ）

前期の授業やこれまでのマークアップでは、デザインカンプ（XDやFigma）の数値をそのまま `font-size: 16px;` や `margin-bottom: 24px;` と指定してきました。
pxは「画面上のピクセル数」に直接対応する**絶対単位（Absolute Unit）**であるため、直感的で分かりやすいというメリットがあります。

しかし、Webの世界において **「文字サイズを px で固定すること」は、現代のアクセシビリティ基準において大きな問題** とされています。

---

## 3-1. ブラウザのフォントサイズ変更機能が無視される問題

Webブラウザ（Google Chrome, Safari, Edgeなど）には、視覚に障害を持つ方や小さな文字が読みづらい高齢者・ロービジョン（弱視）のユーザーのために、**「標準のフォントサイズを好みの大きさに変更する機能」** が備わっています。

### 【実験】ブラウザのフォントサイズを変更してみよう

1. Google Chrome の右上メニュー（︙）から「設定」を開きます。
2. 左メニュー「デザイン」→「フォントサイズ」を確認します（初期状態は「中（推奨）」）。
3. これを **「極大」** に変更してみましょう。

![Chromeフォントサイズ設定画面](05_%E6%A7%98%E3%80%85%E3%81%AA%E5%8D%98%E4%BD%8D/01.png)

設定を変更した状態で、以下の2つのWebサイトを見比べてみてください：

- **Apple 公式サイト（https://www.apple.com/jp/）**
- **Yahoo! JAPAN（https://www.yahoo.co.jp/）**

ブラウザの設定を「極大」にしたにもかかわらず、**pxで文字サイズを固定しているWebサイトでは、テキストの大きさが一切変わりません。**
ユーザーが「文字を大きくして読みたい」と明示的に設定しているにもかかわらず、制作側のコードがそれを無視してしまうのです。

<aside>
⚠️

**「ブラウザのズーム（Cmd + プラスキー）」との違い**

ブラウザの画面全体を拡大する「ズーム（ページ拡大）」であれば、px指定の文字も拡大されます。
しかし、ズームを使うと画像もボタンもすべて巨大化し、画面横スクロールが発生して極めて閲覧しづらくなります。
アクセシビリティ上求められているのは、**「画像やレイアウトの比率は保ちつつ、テキストの可読性だけをユーザーの視力に合わせてスケールさせること」** です。

</aside>

## 3-2. Webアクセシビリティ基準（WCAG）の要件

世界的なWebアクセシビリティのガイドラインである **WCAG（Web Content Accessibility Guidelines）2.1 / 2.2** の達成基準 1.4.4（テキストのサイズ変更）では、以下のように定められています：

> **達成基準 1.4.4（テキストのサイズ変更 - レベルAA）：**
> 支援技術なしで、コンテンツ又は機能を損なうことなく、テキストを 200% までサイズ変更できること。

文字サイズを相対単位（`rem` など）で記述していれば、ユーザーのブラウザ設定に追従して文字が自然に拡大され、誰にとっても読みやすいWebサイトを提供できます。

## 3-3. レスポンシブ対応の記述量と保守性の問題

pxだけでレスポンシブWebデザインを作ろうとすると、画面幅ごとにすべてのプロパティを上書きしなければなりません。

```scss
// ❌ 悪い例：ブレイクポイントごとにすべてのpxを手動で上書きし続ける
.hero-title {
  font-size: 24px;
  margin-bottom: 16px;

  @media (width >= 768px) {
    font-size: 36px;
    margin-bottom: 24px;
  }

  @media (width >= 1200px) {
    font-size: 48px;
    margin-bottom: 32px;
  }
}
```

要素が数十〜数百個に増えたとき、メディアクエリ内で何千行ものpx上書きコードを書くことになり、修正漏れやレイアウト崩れ（デグレ）が頻発します。
これを解決するのが **「相対単位」** です。

# 4. 相対単位の仕組みと使い分け

相対単位とは、**「何らかの基準となる値に対して、何倍・何パーセントか」** を指定する単位です。

| 単位 | 読み方 | 基準とする対象（何に対する相対値か） | 主な使用用途 |
|:---:|:---:|---|---|
| **`%`** | パーセント | **親要素**の同じプロパティ（幅・余白なら親の幅、font-sizeなら親のfont-size） | コンテナ幅、グリッドの列幅 |
| **`em`** | エム | **親要素のfont-size**（文字サイズ指定時）<br>**自分自身のfont-size**（margin, padding, width指定時） | 文字数に応じた幅、ボタンの内側余白連動、letter-spacing |
| **`rem`** | レム（Root EM） | **ルート要素（`<html>`）のfont-size** | **文字サイズ、余白（margin/padding）の現代標準** |
| **`vw`** | ヴィーダブリュー | **ビューポート（画面表示領域）の横幅**の 1% | 画面いっぱいのレイアウト、流体文字サイズ |
| **`vh`** | ヴィーエイチ | **ビューポート（画面表示領域）の高さ**の 1% | フルスクリーンヒーローセクション |
| **`dvh`** | ディーヴィーエイチ | **動的ビューポートの高さ**（スマホのアドレスバー伸縮に追従） | スマホ全画面表示 |

それぞれの単位の特性と、実務での注意点を詳しく見ていきましょう。

---

## 4-1. %（パーセント）

`%` はもっとも古くから使われている相対単位です。

- **`width` や `margin`, `padding`**：基本は **親要素の横幅（width）** に対する割合。
- **`font-size`**：**親要素のフォントサイズ** に対する割合。

```scss
// 親要素（width: 1000px）の中にある子要素
.child {
  width: 50%; // 親要素の横幅の50% = 500px
  margin-left: 5%; // 親要素の横幅の5% = 50px
}
```

<aside>
💡

**注意：縦方向の margin / padding に `%` を指定した場合**

CSSの仕様上、`margin-top: 10%;` や `padding-top: 10%;` のパーセント基準は「親要素の高さ」ではなく、**「親要素の横幅（width）」** になります。
直感と異なる挙動になりやすいため、余白の指定に `%` を多用することは避け、後述する `rem` を使うのが実務の基本です。

</aside>

---

## 4-2. em（エム）

`em`（エム）という名前は、活版印刷の時代に大文字の「M」の正方形の幅を基準としていたことに由来します。

### emの二面性に注意！

1. **`font-size` に指定した場合**：**「親要素のフォントサイズ」** に対する倍率。
2. **`padding`, `margin`, `width` に指定した場合**：**「その要素自身のフォントサイズ」** に対する倍率。

```scss
// 1. font-sizeに指定（親が 16px の場合）
.parent {
  font-size: 16px;

  .child {
    font-size: 1.5em; // 16px × 1.5 = 24px
  }
}

// 2. padding/marginに指定（自分自身のfont-sizeが基準！）
.btn {
  font-size: 20px;
  padding: 0.5em 1em; // 上下: 20px × 0.5 = 10px / 左右: 20px × 1 = 20px
}
```

### 【超重要】emの最大の落とし穴：「コンパウンド現象（掛け算事故）」

`em` でフォントサイズを指定すると、HTMLが入れ子（ネスト）になった際に **親の文字サイズが掛け算（雪だるま式）で増殖する問題** が発生します。

```html
<!-- リストが入れ子になっている構造 -->
<ul class="nav">
  <li>第1階層
    <ul>
      <li>第2階層
        <ul>
          <li>第3階層</li>
        </ul>
      </li>
    </ul>
  </li>
</ul>
```

```scss
// ❌ font-sizeにemを使ってしまうと...
.nav {
  font-size: 1.2em; // 16px × 1.2 = 19.2px

  ul {
    font-size: 1.2em; // 19.2px × 1.2 = 23.04px！（親の親よりどんどん巨大化する）
  }
}
```

階層が深くなるほど文字が勝手に巨大化（あるいは `0.8em` だと微小化）してしまい、スタイルの予測が極めて困難になります。
このため、**「フォントサイズの指定に em を使うこと」は現代のWeb制作では原則として非推奨** です。

---

## 4-3. rem（レム = Root EM）★現代の基本単位

`em` のネスト問題を根本から解決するために CSS3 で登場したのが **`rem（Root EM）`** です。

- **`rem` の基準**：親要素が何重にネストされていようと関係なく、**常にルート要素（`<html>` タグ）のフォントサイズ** だけを参照します。

```scss
// ルート（html）が 16px の場合
html {
  font-size: 16px; // ブラウザ標準
}

.nav {
  font-size: 1.2rem; // 16px × 1.2 = 19.2px

  ul {
    font-size: 1.2rem; // どこまでネストしても 16px × 1.2 = 19.2px のまま！
  }
}
```

### em と rem の違い（図解）

```
【em の場合：親要素を基準にするため雪だるま式に変化する】
<html> (16px)
  └── <body> (1.2em = 19.2px)
        └── <div class="card"> (1.2em = 23.04px)
              └── <p> (1.2em = 27.64px)  ← 意図せずどんどん巨大化！

【rem の場合：常に一番上の <html> だけを参照する】
<html> (16px)
  └── <body> (1.2rem = 19.2px)
        └── <div class="card"> (1.2rem = 19.2px)
              └── <p> (1.2rem = 19.2px)  ← 何重にネストしても常に同じ大きさ！
```

### rem を使う絶大なメリット

1. **予測可能性が高い（PREDICTABLE）**：親要素のスタイルに左右されず、常にルート基準で一貫したサイズが保たれる。
2. **アクセシビリティに完全対応**：ブラウザの文字サイズ設定を変更した際、ルートのフォントサイズがスケールするため、サイト全体の文字と余白が美しく連動拡大する。
3. **ルート（`<html>`）を1箇所書き換えるだけで、サイト全体の拡大縮小が一瞬で可能**。

---

## 4-4. では、`em` はもう使わないのか？（実務での em の使い所）

`rem` が主流になった現代でも、**「あえて em を使うべき絶好のシチュエーション」** が3つあります。

### ① ボタンUIのプロポーション連動（文字サイズと内側余白の同期）

ボタンの内側余白（padding）に `em` を指定しておくと、モディファイアでフォントサイズを変えるだけで、**ボタンの余白バランス（プロポーション）が自動的にスケール** します。

```scss
.btn {
  display: inline-block;
  padding: 0.6em 1.5em; // 文字サイズに対して「上下0.6文字分」「左右1.5文字分」
  font-size: 1rem; // 基本サイズ（16px）
  border-radius: 9999px;
  background-color: #e40065;
  color: #fff;

  // 大ボタン（文字を大きくするだけで、パディングも自動で広がる！）
  &--large {
    font-size: 1.5rem; // 24px相当
    // paddingを再定義する必要がない！
  }

  // 小ボタン（文字を小さくするだけで、パディングも自動で引き締まる！）
  &--small {
    font-size: 0.75rem; // 12px相当
  }
}
```

### ② `letter-spacing`（字間）の指定

デザインカンプ（Adobe XD や Figma）の文字間隔（トラッキング）は、多くの場合 `em` で指定するのが鉄則です。
フォントサイズが変わっても、字間の比率が自動的に保たれるためです。

```scss
// XDのトラッキング値が「50」の場合 → 50 / 1000 = 0.05em
.heading {
  font-size: 2rem;
  letter-spacing: 0.05em;
}
```

### ③ 文字数に基づいた幅の制御（アイコンやラベル）

「3文字分の幅をピッタリ確保したい」「全角2文字分インデントしたい」といった場合、`width: 3em;` や `text-indent: 2em;` と書くことで、フォントサイズ変更に強い堅牢なレイアウトが作れます。

## 4-5. ビューポート単位（vw, vh, svh, dvh, lvh）

ブラウザの画面サイズ（Viewport）に直接連動する単位です。

- **`1vw`**：画面横幅の 1%（画面幅が 1200px なら 12px）
- **`1vh`**：画面高さの 1%（画面高が 800px なら 8px）

### 【注意】`100vw` を使ってはいけない理由

画面いっぱいに広げたいときに `width: 100vw;` と書いてしまいがちですが、**これはNG** です。
なぜなら、`100vw` は **「ブラウザの垂直スクロールバーの幅を含んだ横幅」** を計算してしまうためです。
ページが縦長でスクロールバーが出ている場合、`100vw` を指定した要素は画面外にはみ出し、**下部に不要な横スクロールバー（横揺れバグ）が発生** します。

```scss
// ❌ 悪い例：横スクロールバーが発生する危険大
.hero {
  width: 100vw;
}

// ⭕️ 正しい例：スクロールバーを除いたコンテンツ幅いっぱいに広がる
.hero {
  width: 100%;
}
```

### スマホの「100vh問題」とモダンな解決策（`dvh`, `svh`, `lvh`）

スマートフォン（iOS Safari や Android Chrome）では、画面をスクロールするとアドレスバーやツールバーが出現したり隠れたりします。
従来の `100vh` はアドレスバーが隠れた状態の最大高さを基準にしていたため、**「スマホで見ると最下部のボタンがアドレスバーに隠れて押せない！」** という深刻な問題がありました。

これを解決するために新しく導入されたのが以下の3つの単位です：

| 単位 | 正式名称 | 特徴 |
|:---:|:---:|---|
| **`svh`** | Small Viewport Height | アドレスバーが **表示されている状態** の最も小さい画面高さを基準にする |
| **`lvh`** | Large Viewport Height | アドレスバーが **隠れた状態** の最も大きい画面高さを基準にする |
| **`dvh`** | Dynamic Viewport Height | アドレスバーの出し入れに合わせて **リアルタイムに可変する** 画面高さを基準にする |

```scss
// スマホで綺麗にファーストビューを全画面表示したい場合
.mainvisual {
  height: 100vh; // 古いブラウザ用のフォールバック
  height: 100dvh; // アドレスバーの伸縮にリアルタイムに追従する最新指定！
}
```

# 5. ルートフォントサイズの設計戦略

`rem` の良さは理解できても、1つ大きな疑問が湧きます。
**「デザインカンプが px で作られているのに、いちいち 16 で割り算して rem を計算するのは面倒じゃないか？」** という点です。

例えば、デザインカンプで文字サイズが `28px` だった場合：
`28 ÷ 16 = 1.75rem` と電卓を叩く必要があります。

この計算の手間を解消するために、現場では主に **2つのアプローチ** が使われてきました。

---

## 5-1. アプローチA：「html { font-size: 62.5%; }」手法（古典的ハック）

Web制作の歴史の中で、古くから広く使われてきた有名なテクニックが **「62.5% 指定」** です。

```css
html {
  font-size: 62.5%; /* 16px × 62.5% = 10px になる！ */
}

body {
  font-size: 1.6rem; /* 10px × 1.6 = 16px（基準に戻す） */
}

h1 {
  font-size: 2.8rem; /* 10px × 2.8 = 28px（電卓不要！小数点をずらすだけ） */
}

p {
  font-size: 1.4rem; /* 10px × 1.4 = 14px */
}
```

### なぜ 62.5% なのか？
ブラウザのデフォルト文字サイズは通常 `16px` です。
`16px × 0.625 = 10px` となり、**ルート要素が「10px」相当** になります。
すると、`24px → 2.4rem`、`32px → 3.2rem` のように、**カンプの数値を10で割る（小数点を左に1つ移動する）だけで暗算できる** ようになります。

### 【注意】62.5% 指定のデメリット
一見便利に見えるこの手法ですが、現代の制作では以下のデメリットがあり、採用が見送られるケースが増えています：

1. **外部コンポーネントとの衝突**：BootstrapやTailwind CSS、WordPressプラグインなどのサードパーティ製ライブラリを読み込んだ際、ライブラリ側は「ルート=16px」を前提に作られているため、デザインが極端に縮小して崩れる。
2. **直感的でないCSS**：`font-size: 62.5%` という謎の数値をCSSの先頭に必ず置く必要があり、初見の開発者が混乱する。

---

## 5-2. アプローチB：Sass関数 `@function rem($px)` によるモダンな解法（★推奨）

Sassを使える環境であれば、`html` に不自然なハックを加える必要はありません。
**「`html` は標準の 16px（100%）のままにしておき、Sassの関数で px を rem に自動変換させる」** のが最も美しく安全なアプローチです。

```scss
@use "sass:math";

// 基準となるルートフォントサイズ（ブラウザ標準）
$font-size-base: 16;

// pxをremに変換するSass関数
// @param {number} $px-value - デザインカンプのpx値
// @return {string} - 計算されたrem値
@function rem($px-value) {
  @return #{math.div($px-value, $font-size-base)}rem;
}

// XD/Figmaのトラッキング値をemに変換するSass関数
// @param {number} $xd-value - カンプのトラッキング値（例: 50, 100）
// @return {string} - 計算されたem値
@function ls($xd-value) {
  @return #{math.div($xd-value, 1000)}em;
}
```

### 実際のコーディングでの使い方

```scss
body {
  font-size: rem(14); // 自動で 0.875rem にコンパイルされる！
  letter-spacing: ls(50); // 自動で 0.05em にコンパイルされる！
}

.hero__title {
  font-size: rem(36); // 自動で 2.25rem にコンパイルされる！
  margin-bottom: rem(24); // 自動で 1.5rem にコンパイルされる！
}
```

```css
/* コンパイル後の CSS */
body {
  font-size: 0.875rem;
  letter-spacing: 0.05em;
}

.hero__title {
  font-size: 2.25rem;
  margin-bottom: 1.5rem;
}
```

電卓を叩く必要は一切なく、**「カンプのpx数値をそのまま `rem(28)` と書くだけ」** で、ブラウザには正しい `rem` が出力されます。
外部ライブラリとも一切衝突せず、アクセシビリティも100%担保されます。

# 6. スペーシング・スケール（Spacing Scale）

`rem()` 関数を使えば自由自在にpxからremへ変換できますが、ここでもう一つ実務上の重要な問題が発生します。
デザインカンプを測ったときに、余白が **`18px`**, **`21px`**, **`23px`**, **`25px`** のようにバラバラだった経験はありませんか？

このように場当たり的な数値（マジックナンバー）をそのまま `rem(21);` や `rem(23);` と打ち込んでいると、以下の破綻が生じます：

1. **デザインのリズム（一貫性）が崩れる**：パーツごとに微妙に余白が異なり、全体として素人くさい印象になる。
2. **保守性が最悪になる**：「サイト全体の余白感を少し広げたい」となったとき、数百箇所の数値を手作業で修正することになる。

---

## 6-1. 8pxグリッドとスペーシング・スケールの導入

Webデザインのスタンダードでは、**「4px または 8px の倍数」** で余白を統一する「8pxグリッドシステム」が採用されています。
これに合わせて、サイト全体で使う余白を `rem` 単位のSass変数として定義したものを **「スペーシング・スケール（Spacing Scale）」** と呼びます。

```scss
// =================================================================
//  Spacing Scale（余白の段階設計）
//  ※ ルートフォントサイズ 16px を基準とする
// =================================================================
$space-xs:    0.25rem; //  4px (極小：アイコンと文字の間など)
$space-s:     0.5rem;  //  8px (小：タグの内側、ボタンの上下など)
$space-m:     1rem;    // 16px (中：コンポーネント内の基本余白)
$space-l:     1.5rem;  // 24px (大：見出しと本文の間など)
$space-xl:    2rem;    // 32px (特大：カード同士の間隔など)
$space-xxl:   2.5rem;  // 40px (巨大：セクション内の大きな区切り)
$space-xxxl:  3rem;    // 48px
$space-xxxxl: 5rem;    // 80px (セクション間の上下余白)
$space-xxxxxl:7.5rem;  // 120px
```

### 実務での適用例

```scss
.card {
  padding: $space-xl $space-l; // 上下32px、左右24px相当
  border-radius: $space-s;

  &__title {
    margin-bottom: $space-m; // 16px相当
  }

  &__tag {
    margin-right: $space-xs; // 4px相当
  }
}
```

デザイナーとエンジニアが「この余白は `$space-l` ね」と共通言語を持つことで、無駄な迷いがなくなり、サイト全体のデザインが驚くほど整います。

<aside>
💡

**スケール以外の数値が出てきたら？**

「どうしてもこのバナーだけ 18px の余白が必要」という例外的な箇所に限って、先ほどの `@function rem(18)` を使います。
**「基本はスペーシング変数 `$space-*` を使い、例外のみ `rem()` 関数を使う」** というルールにしておくと、コードの一貫性が保たれます。

</aside>

# 7. CSSカスタムプロパティ（CSS変数）

前期および前回では「Sassの変数（`$variable`）」を学びました。
しかし現在では、CSSの公式仕様としてブラウザ自身が解釈できる **「CSSカスタムプロパティ（CSS Variables / ネイティブCSS変数）」** が利用可能です。

---

## 7-1. CSSカスタムプロパティの構文

CSS変数は、ハイフン2つ（`--`）で始まる名前で定義し、`var(--変数名)` で呼び出します。

```css
/* 1. 定義（通常は最上位の :root に書く） */
:root {
  --color-primary: #e40065;
  --color-text: #2f2f2f;
  --base-radius: 8px;
}

/* 2. 呼び出し */
.button {
  background-color: var(--color-primary);
  color: #fff;
  border-radius: var(--base-radius);
}

.button--secondary {
  /* フォールバック（未定義時の代替値）も指定可能 */
  background-color: var(--color-sub, #666);
}
```

<aside>
💡

**`:root` とは？**

`:root` は、HTMLドキュメントの最も根本にある要素（`<html>` タグ）を指す擬似クラスです。
`:root` で定義された変数は、ページ内のすべての要素（グローバル）から参照できます。

</aside>

---

## 7-2. Sass変数（`$var`） vs CSSカスタムプロパティ（`--var`）徹底比較

「Sass変数があるのに、なぜわざわざCSS変数を使う必要があるのか？」
この2つには、**「いつ処理されるか」** という決定的な違いがあります。

| 比較項目 | Sass変数（`$var`） | CSSカスタムプロパティ（`--var`） |
|---|---|---|
| **処理されるタイミング** | **コンパイル時（ビルド時）** に静的に展開される | **ブラウザ実行時（ランタイム）** に動的に評価される |
| **ブラウザの認識** | CSSになった時点でただの固定値になり、変数は消滅する | ブラウザ自身が変数のまま保持している |
| **メディアクエリでの更新** | ❌ **不可**（メディアクエリ内で変数を上書きしても他に波及しない） | ⭕️ **可能**（画面幅に応じて変数の値そのものを差し替えられる） |
| **JavaScriptからの操作** | ❌ **不可**（JSからは見えない） | ⭕️ **可能**（`style.setProperty()` で動的に変更可能） |
| **Sass関数での演算** | ⭕️ **可能**（`math.div()` や色計算関数に渡せる） | ❌ **不可**（Sassコンパイラは中身を動的な文字列として扱うため） |
| **スコープと継承** | Sassファイル内のみ | **DOMツリーに沿ってカスケード（継承）する** |

### 【比較実験】メディアクエリでの挙動の違い

```scss
// ❌ Sass変数はメディアクエリで値を動的に変えられない
$container-padding: 16px;

@media (width >= 768px) {
  $container-padding: 40px; // これはメディアクエリ内部の局所スコープで終わる
}

.container {
  padding: $container-padding; // 常に 16px のまま！
}
```

```css
/* ⭕️ CSS変数なら、メディアクエリ内で変数を書き換えるだけで全パーツに波及する！ */
:root {
  --container-padding: 1rem;
}

@media (width >= 768px) {
  :root {
    --container-padding: 2.5rem; /* 変数の値を上書き！ */
  }
}

.container {
  padding: var(--container-padding); /* 自動で 2.5rem に切り替わる！ */
}
```

---

## 7-3. 実務での使い分けベストプラクティス

現代のプロの現場では、「どちらか一方だけを使う」のではなく、**それぞれの強みを活かして併用** します。

```
┌─────────────────────────────────────────────────────────┐
│  Sass変数（$var）を使うべきところ                        │
│  ・Sassの演算や @function で計算に使う数値               │
│  ・ブレイクポイント（$breakpoints: (desktop: 768px)）    │
│  ・Sass内部のファイル設計・ビルド専用の設定フラグ        │
└─────────────────────────────────────────────────────────┘
                            ▼
┌─────────────────────────────────────────────────────────┐
│  CSS変数（--var）を使うべきところ                        │
│  ・テーマカラー（ダークモード切替、ブランドカラー）       │
│  ・メディアクエリで動的に変化させたい余白やグリッド列数  │
│  ・JavaScriptから動的に変更するプロパティ                │
│  ・コンポーネント固有のカスタマイズ（局所スコープ）      │
└─────────────────────────────────────────────────────────┘
```

# 8. 流体タイポグラフィ（Fluid Typography）と `clamp()`

これまでのレスポンシブは、「スマホ用の文字サイズ」と「PC用の文字サイズ」をメディアクエリ（ブレイクポイント）でカクッと切り替えるのが主流でした。
しかし、これでは **「スマホとPCの中間サイズ（タブレット等）」で文字が不自然に大きすぎたり小さすぎたりする問題** が起こります。

これを解決するのが、CSSの比較関数 **`clamp()`** を使った **「流体タイポグラフィ（Fluid Typography）」** です。

---

## 8-1. `clamp()` の構文

```css
font-size: clamp(最小値, 推奨値, 最大値);
```

- **最小値（下限ガード）**：どれだけ画面が小さくなっても、これ以上は小さくならない下限。
- **推奨値（可変値）**：画面幅に応じてスムーズに伸縮する値（通常 `vw` を組み込む）。
- **最大値（上限ガード）**：どれだけ画面が巨大になっても、これ以上は大きくならない上限。

```scss
// 使用例：見出し文字サイズ
h1 {
  font-size: clamp(1.5rem, 4vw, 3rem);
}
```

### このコードの挙動

1. **画面幅が狭いスマホ**：`4vw` の計算結果が `1.5rem（24px）` を下回っても、**最小値の `1.5rem` でピタッと止まる**（小さすぎて読めなくなる事故を防ぐ）。
2. **画面幅が広い大画面PC**：`4vw` の計算結果が `3rem（48px）` を上回っても、**最大値の `3rem` でピタッと止まる**（巨大化して画面を圧迫する事故を防ぐ）。
3. **その中間の画面（タブレットやノートPC）**：`4vw` に連動して、**一切ブレイクポイントのガタつきなく、滑らかに文字サイズが無段階伸縮する！**

<aside>
💡

**メディアクエリを書かずにレスポンシブが完結する！**

`clamp()` を使うと、1行のコードで「スマホ〜タブレット〜PC」のすべての画面サイズに完璧に適応します。
メディアクエリを何行も書いて上書きする必要がなくなるため、コードが劇的にスリムになります。
文字サイズだけでなく、`padding: clamp(1rem, 5vw, 4rem);` のようにセクションの余白にも極めて有効です。

</aside>

# 9. 実務チートシート：プロパティ別の単位選定基準

「結局、どのプロパティにどの単位を使えばいいの？」と迷ったときは、以下の実務基準に従ってください。

| プロパティ | 推奨単位 | 理由・選定の根拠 |
|---|:---:|---|
| **`font-size`** | **`rem`**<br>（または `clamp()`） | アクセシビリティ（ブラウザの文字サイズ変更）に対応するため。カスケード事故を防ぐ。大見出しは `clamp()` で流体化。 |
| **`line-height`** | **単位なし数値**<br>（例: `1.7`） | 単位なしの倍率で指定すると、フォントサイズ変更時に常に適切な行間比率が子要素にも正しく継承される（`px` や `%` はNG）。 |
| **`letter-spacing`** | **`em`**<br>（例: `0.05em`） | カンプのトラッキング値を変換。フォントサイズが変わっても同じ字間比率を維持できる。 |
| **`width` / `max-width`** | **`%`** / **`rem`** / **`px`** | コンテナ幅は `%` や `rem`。文字数に連動させたいラベルやボタンは `em`。 |
| **`height`** | **指定しない**<br>（または `dvh` / `aspect-ratio`） | 高さは中身のテキスト量に応じて成り行き（`auto`）にするのが基本。全画面表示のみ `100dvh` を使用。 |
| **`margin` / `padding`** | **`rem`**<br>（スペーシング変数） | ルートの文字サイズと連動して余白もスケーリングさせる。ボタンのプロポーション連動のみ `em` を使用。 |
| **`border-width`** | **`px`**<br>（例: `1px`, `2px`） | 境界線は画面サイズによって太くしたくないため、固定の絶対値（`px`）で指定するのが自然。 |
| **`border-radius`** | **`rem`** / **`px`** / **`9999px`** | 角丸を文字サイズに追従させたい場合は `rem`。完全なカプセル型ボタンは `9999px`（または `50vh`）。 |

  --color-text: #000000;
  --color-base: #2f2f2f;
  --color-bg: #f4f4f4;
}

//  Variables (Sass)
// =================================================================

$space-m: 1rem; // 16px
$space-l: 1.5rem; // 24px

$space-xxl: 2.5rem; // 40px
$space-xxxl: 3rem; // 48px
$space-xxxxl: 5rem; // 80px
$space-xxxxxl: 7.5rem; // 120px

// --- Typography ---
$font-size-base: 16;
$font-family-gothic: "Noto Sans JP", "Helvetica Neue", Arial, "Hiragino Kaku Gothic ProN", "Hiragino Sans", "Yu Gothic", Meiryo, sans-serif;
$font-family-mincho: "Times New Roman", Times, "Hiragino Mincho ProN", "Yu Mincho", "MS PMincho", serif;

// --- Breakpoints ---
$breakpoints: (
  "mobile": 480px,
  "tablet": 768px,
  "desktop": 1024px,
);

// =================================================================
//  Functions
// =================================================================

// pxをremに変換する

@mixin mq($breakpoint: desktop) {

}

// コンテナ幅・インナー中央寄せ

// @param {number} $w  - width (基本は %)
@mixin inner($mw: 1000px, $w: 90%) {
  max-width: $mw;
  width: $w;
  margin-left: auto;
  margin-right: auto;
}
```

      "  margin-left: auto;",
      "  margin-right: auto;",
      "}"
    ]
  }
}
```

これで、新規の `.scss` ファイルで **`!kit`** と入力して Tab キーまたは Enter キーを押すだけで、いつでも完璧な設計テンプレートが呼び出せます。

## 11-1. 授業内演習：CUBE HAUS の rem & CSS変数リファクタリング

1. **スターターキットの導入**：`sass/style.scss` の冒頭に `!kit` を展開し、サイト固有のカラーコードを変数化する。

   - 共通の余白（16px, 24px, 40pxなど）を `$space-m`, `$space-l`, `$space-xxl` に置き換える。

   - メインカラー（`#e40065`）や背景色を CSSカスタムプロパティ（`--color-main`）として管理する。

## 11-2. 課題：Mache のマークアップ（または指定の課題データ）

「BEM」「Sass（SCSS）」「rem設計」「スペーシング変数」のルールに則って、課題データ（`09-mache-rem` または授業で案内される課題データ）をマークアップしてください。

[HTML+CSS 課題データ - Google Drive](https://drive.google.com/drive/folders/1TerVbEHQw_gibRX-d6709S3wUu9QeoBk?usp=sharing)

### 【課題のクリア条件】

1. **フォントサイズに px を使わないこと**：すべて `rem()` 関数（または `clamp()`）で指定すること。
2. **余白の変数化**：以下の基準余白は、必ずスペーシング変数（`$space-*`）を使用すること。
   ```scss
   $space-s:   0.5rem;  //  8px
   $space-m:   1rem;    // 16px
   $space-l:   1.5rem;  // 24px
   $space-xl:  2rem;    // 32px
   $space-xxl: 2.5rem;  // 40px
   $space-xxxl:3rem;    // 48px
   ```
   ※上記以外の端数が出た場合は、`rem(数値)` 関数で指定すること。
3. **字間（letter-spacing）の関数化**：カンプの数値を `ls(数値)` 関数で指定すること。
4. **モジュール設計の徹底**：複数箇所で使われるパーツ（ボタン、カード、投稿リストなど）は BEM の独立した Block としてマークアップすること。
5. **ヘッダー固定の制御**：ヘッダーはスクロール時も上部に固定配置（`position: sticky;` または `position: fixed;`）すること。

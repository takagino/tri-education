# 3. なぜ「px」だけではいけないのか？（絶対単位の限界とアクセシビリティ）

前期の授業やこれまでのマークアップでは、デザインカンプ（XDやFigma）の数値をそのまま `font-size: 16px;` や `margin-bottom: 24px;` と指定してきました。
pxは「画面上のピクセル数」に直接対応する**絶対単位（Absolute Unit）**であるため、直感的で分かりやすいというメリットがあります。

しかし、Webの世界において **「文字サイズを px で固定すること」は、現代のアクセシビリティ基準において大きな問題** とされています。

---

## 3-1. ブラウザのフォントサイズ変更機能が無視される問題

Webブラウザ（Google Chrome, Safari, Edgeなど）には、視覚に障害を持つ方や小さな文字が読みづらい高齢者・ロービジョン（弱視）のユーザーのために、**「標準のフォントサイズを好みの大きさに変更する機能」** が備わっています。

### 【実験】ブラウザのフォントサイズを変更してみよう

1. Google Chrome の右上メニュー（︙）から「設定」を開きます。
2. 左メニュー「デザイン」→「フォントサイズ」を確認します（初期状態は「中（推奨）」）。
3. これを **「極大」** に変更してみましょう。

![Chromeフォントサイズ設定画面](05_%E6%A7%98%E3%80%85%E3%81%AA%E5%8D%98%E4%BD%8D/01.png)

設定を変更した状態で、以下の2つのWebサイトを見比べてみてください：

- **Apple 公式サイト（https://www.apple.com/jp/）**
- **Yahoo! JAPAN（https://www.yahoo.co.jp/）**

ブラウザの設定を「極大」にしたにもかかわらず、**pxで文字サイズを固定しているWebサイトでは、テキストの大きさが一切変わりません。**
ユーザーが「文字を大きくして読みたい」と明示的に設定しているにもかかわらず、制作側のコードがそれを無視してしまうのです。

<aside>
⚠️

**「ブラウザのズーム（Cmd + プラスキー）」との違い**

ブラウザの画面全体を拡大する「ズーム（ページ拡大）」であれば、px指定の文字も拡大されます。
しかし、ズームを使うと画像もボタンもすべて巨大化し、画面横スクロールが発生して極めて閲覧しづらくなります。
アクセシビリティ上求められているのは、**「画像やレイアウトの比率は保ちつつ、テキストの可読性だけをユーザーの視力に合わせてスケールさせること」** です。

</aside>

## 3-2. Webアクセシビリティ基準（WCAG）の要件

世界的なWebアクセシビリティのガイドラインである **WCAG（Web Content Accessibility Guidelines）2.1 / 2.2** の達成基準 1.4.4（テキストのサイズ変更）では、以下のように定められています：

> **達成基準 1.4.4（テキストのサイズ変更 - レベルAA）：**
> 支援技術なしで、コンテンツ又は機能を損なうことなく、テキストを 200% までサイズ変更できること。

文字サイズを相対単位（`rem` など）で記述していれば、ユーザーのブラウザ設定に追従して文字が自然に拡大され、誰にとっても読みやすいWebサイトを提供できます。

## 3-3. レスポンシブ対応の記述量と保守性の問題

pxだけでレスポンシブWebデザインを作ろうとすると、画面幅ごとにすべてのプロパティを上書きしなければなりません。

```scss
// ❌ 悪い例：ブレイクポイントごとにすべてのpxを手動で上書きし続ける
.hero-title {
  font-size: 24px;
  margin-bottom: 16px;

  @media (width >= 768px) {
    font-size: 36px;
    margin-bottom: 24px;
  }

  @media (width >= 1200px) {
    font-size: 48px;
    margin-bottom: 32px;
  }
}
```

要素が数十〜数百個に増えたとき、メディアクエリ内で何千行ものpx上書きコードを書くことになり、修正漏れやレイアウト崩れ（デグレ）が頻発します。
これを解決するのが **「相対単位」** です。

---

# 4. 相対単位の仕組みと一覧

相対単位とは、**「何らかの基準となる値に対して、何倍・何パーセントか」** を指定する単位です。

| 単位 | 読み方 | 基準とする対象（何に対する相対値か） | 主な使用用途 |
|:---:|:---:|---|---|
| **`%`** | パーセント | **親要素**の同じプロパティ（幅・余白なら親の幅、font-sizeなら親のfont-size） | コンテナ幅、グリッドの列幅 |
| **`em`** | エム | **親要素のfont-size**（文字サイズ指定時）<br>**自分自身のfont-size**（margin, padding, width指定時） | 文字数に応じた幅、ボタンの内側余白連動、letter-spacing |
| **`rem`** | レム（Root EM） | **ルート要素（`<html>`）のfont-size** | **文字サイズ、余白（margin/padding）の現代標準** |
| **`vw`** | ヴィーダブリュー | **ビューポート（画面表示領域）の横幅**の 1% | 画面いっぱいのレイアウト、流体文字サイズ |
| **`vh`** | ヴィーエイチ | **ビューポート（画面表示領域）の高さ**の 1% | フルスクリーンヒーローセクション |
| **`dvh`** | ディーヴィーエイチ | **動的ビューポートの高さ**（スマホのアドレスバー伸縮に追従） | スマホ全画面表示 |

それぞれの単位の特性と、実務での注意点を詳しく見ていきましょう。

---

# 5. %（パーセント）

`%` はもっとも古くから使われている相対単位です。

- **`width` や `margin`, `padding`**：基本は **親要素の横幅（width）** に対する割合。
- **`font-size`**：**親要素のフォントサイズ** に対する割合。

```scss
// 親要素（width: 1000px）の中にある子要素
.child {
  width: 50%; // 親要素の横幅の50% = 500px
  margin-left: 5%; // 親要素の横幅の5% = 50px
}
```

<aside>
💡

**注意：縦方向の margin / padding に `%` を指定した場合**

CSSの仕様上、`margin-top: 10%;` や `padding-top: 10%;` のパーセント基準は「親要素の高さ」ではなく、**「親要素の横幅（width）」** になります。
直感と異なる挙動になりやすいため、余白の指定に `%` を多用することは避け、後述する `rem` を使うのが実務の基本です。

</aside>

# 6. em（エム）

`em`（エム）という名前は、活版印刷の時代に大文字の「M」の正方形の幅を基準としていたことに由来します。

---

## 6-1. emの二面性に注意！（プロパティによって基準が変わる）

`em` を扱う上で最も混乱しやすいのが、**「どのプロパティに指定したか」によって基準となる対象がすり替わる** という点です。

| 指定するプロパティ | 基準になるもの | 計算式 |
|---|---|---|
| **`font-size`** | **親要素** のフォントサイズ | 親の `font-size` × `数値em` |
| **`margin` / `padding` / `width` 等** | **その要素自身** のフォントサイズ | 自身の `font-size` × `数値em` |

```scss
// 1. font-size に指定した場合（親要素が基準）
.parent {
  font-size: 16px;

  .child {
    font-size: 1.5em; // 親(16px) × 1.5 = 24px
  }
}

// 2. padding / margin に指定した場合（自分自身が基準！）
.btn {
  font-size: 20px;
  padding: 0.5em 1em; // 上下: 20px × 0.5 = 10px / 左右: 20px × 1 = 20px
}
```

#### 【注意】余白に em を使うと「自分自身のフォントサイズ」を常に把握する必要がある
余白（`margin` や `padding`）に `em` を指定すると、基準は「その要素自身のフォントサイズ」になります。

一見便利そうですが、実務では **「常にその要素自身のフォントサイズを把握しておかないといけないので非常に面倒」** という大きなデメリットがあります。

- **文字サイズを変えると余白まで連動してしまう**: デザイン変更などで `font-size` を変えた際、余白の広さまで勝手に変わってしまいます。
- **計算コストが高い**: 「ここに 16px の余白をつけたい」と思ったとき、その要素のフォントサイズが 14px なのか 18px なのかを都度確認して「16 ÷ 14 = 1.142...em」と計算しなければなりません。

このように、余白のサイズが自分自身のフォントサイズに振り回されてしまうため、通常のレイアウトや余白には **ページ全体で基準がブレない `rem`** を使うのが一般的です。

---

## 6-2. 【超重要】font-size を指定していない要素（divなど）に em を使うとどうなる？

「`div` や `section` に `margin: 2em;` を書いたけれど、その `div` 自体には `font-size` を指定していない。この場合の 1em は何pxになるのか？」

結論から言うと、**CSSの「継承（inherit）」の仕組みにより、親要素のフォントサイズがそのまま基準** になります。

```html
<article class="news-card">
  <div class="news-card__body">
    <p>記事の本文...</p>
  </div>
</article>
```

```scss
.news-card {
  font-size: 16px; // 親要素

  &__body {
    // 自身の font-size は未指定（親の 16px を自動継承）
    margin-bottom: 2em; // 16px × 2 = 32px の余白
  }
}
```

#### ここに潜む危険な落とし穴：「意図しない余白の暴走」
もし後から「カード全体のデザイン調整で、親（`.news-card`）のフォントサイズを `20px` にしよう」と変更したとします。

```scss
.news-card {
  font-size: 20px; // 16px から 20px に拡大！

  &__body {
    margin-bottom: 2em; // 20px × 2 = 40px に勝手に膨張してしまう！
  }
}
```

`.news-card__body` のレイアウトを変えたつもりはないのに、**「親の文字サイズを変えただけで、まったく関係のないブロックの余白まで勝手に伸び縮みしてしまう」** という深刻なレイアウト崩れ（バグ）を引き起こします。

<aside>
💡

**実務の鉄則**

`div` や `section`、`main` といった**レイアウト用コンテナの余白（margin / padding）に `em` を使ってはいけません。**
親要素の文字サイズ変更にレイアウトが巻き込まれてしまうため、余白には必ず後述する **`rem`** を使います。

</aside>

## 6-3. em のその他の注意点と落とし穴

#### 注意点①：コンパウンド現象（掛け算事故・雪だるま事故）
`font-size` に `em` を使い、HTMLタグが入れ子（ネスト）になると、**親の文字サイズが階層ごとに掛け算（雪だるま式）されて増殖** します。

```html
<!-- リストが入れ子になっている構造 -->
<ul class="nav">
  <li>第1階層
    <ul>
      <li>第2階層
        <ul>
          <li>第3階層</li>
        </ul>
      </li>
    </ul>
  </li>
</ul>
```

```scss
// ❌ font-sizeにemを使ってしまうと...
.nav {
  font-size: 1.2em; // 16px × 1.2 = 19.2px

  ul {
    font-size: 1.2em; // 19.2px × 1.2 = 23.04px！（親の親よりどんどん巨大化する）
  }
}
```
階層が深くなるほど文字が勝手に巨大化（`0.8em` なら極小化）し、スタイルの制御が不可能になります。
このため、**「フォントサイズの指定に em を使うこと」は現代のWeb制作では原則NG** です。

#### 注意点②：文中のインライン要素で使うと行間（line-height）がガタつく
文章中の一部の単語だけを目立たせようとして、`<span>` や `<strong>` に `font-size: 1.3em;` などを指定すると、その単語の行だけ `line-height` が押し広げられ、段落全体の行間が不揃いにガタついてしまいます。

```html
<!-- ❌ 行間がガタガタに崩れる原因になる -->
<p>通常のテキストの中に、<span style="font-size: 1.4em;">ここだけ大きい文字</span> が混ざると行の高さが不揃いになる。</p>
```

#### 注意点③：メディアクエリ内の em は「ブラウザ初期値」が基準になる（特殊仕様）
メディアクエリの中で `@media (width >= 40em)` のように `em` を使う場合、ルート（`html`）や親要素でフォントサイズをいくら変更していても**すべて無視され、常にブラウザの初期設定（通常 16px）の 40倍（640px）** として計算されます。

```scss
html {
  font-size: 20px; // この設定はメディアクエリの em には一切影響しない！
}

@media (width >= 40em) { // 常に 16px × 40 = 640px として判定される
  ...
}
```
※ブラウザの文字ズーム設定に連動してメディアクエリを発火させたい実務ハックとして使われることがありますが、特殊な挙動である点に注意が必要です。

## 6-4. では、`em` はもう使わないのか？（実務での em の使い所）

`rem` が主流になった現代でも、**「あえて em を使うべき絶好のシチュエーション」** が3つあります。

### ① ボタンUIのプロポーション連動（文字サイズと内側余白の同期）

ボタンの内側余白（padding）に `em` を指定しておくと、モディファイアでフォントサイズを変えるだけで、**ボタンの余白バランス（プロポーション）が自動的にスケール** します。

```scss
.btn {
  display: inline-block;
  padding: 0.6em 1.5em; // 文字サイズに対して「上下0.6文字分」「左右1.5文字分」
  font-size: 1rem; // 基本サイズ（16px）
  border-radius: 9999px;
  background-color: #e40065;
  color: #fff;

  // 大ボタン（文字を大きくするだけで、パディングも自動で広がる！）
  &--large {
    font-size: 1.5rem; // 24px相当
    // paddingを再定義する必要がない！
  }

  // 小ボタン（文字を小さくするだけで、パディングも自動で引き締まる！）
  &--small {
    font-size: 0.75rem; // 12px相当
  }
}
```

### ② `letter-spacing`（字間）の指定

デザインカンプ（Adobe XD や Figma）の文字間隔（トラッキング）は、多くの場合 `em` で指定するのが鉄則です。
フォントサイズが変わっても、字間の比率が自動的に保たれるためです。

```scss
// XDのトラッキング値が「50」の場合 → 50 / 1000 = 0.05em
.heading {
  font-size: 2rem;
  letter-spacing: 0.05em;
}
```

### ③ 文字数に基づいた幅の制御やレイアウト（ラベル・インデント・アイコン）

`em` は日本語のフォント（等幅）において **「全角1文字分の幅・高さ」** とほぼ等しいため、文字数を基準にしたレイアウトに最適です。

#### 1. フォームのラベル幅を「文字数」でピタッと揃える
文字数が異なる項目名（「氏名」「郵便番号」「メールアドレス」など）の幅を揃えたい場合、`width: 〇em;` を指定すると全角文字数ぴったりの幅を確保できます。

```scss
.form-label {
  display: inline-block;
  width: 6em; // 全角6文字分の幅をピタッと確保！
}
```

#### 2. 注釈の「ぶら下げインデント」（※マークを外に出す）
「※」から始まる注釈文で、2行目以降を1文字分引っ込めたい定番のUIパターンです。文字サイズが変わっても「常に全角1文字分」の幅が正確にキープされます。

```scss
.note {
  padding-left: 1em; // 全角1文字分の左余白をあける
  text-indent: -1em; // 1行目だけ1文字分左に引っ張り出す
}
```

#### 3. テキストの文字サイズに連動するアイコン
SVGアイコンなどの幅・高さを `1em` にしておくと、テキストの `font-size` を変えるだけで、アイコンのサイズも全く同じ大きさに自動スケールします。

```scss
.icon {
  display: inline-block;
  width: 1em;
  height: 1em;
  vertical-align: -0.15em; // テキストとの縦位置を微調整
}
```

# 7. rem（レム = Root EM）★現代の基本単位

`em` のネスト問題を根本から解決するために CSS3 で登場したのが **`rem（Root EM）`** です。

- **`rem` の基準**：親要素が何重にネストされていようと関係なく、**常にルート要素（`<html>` タグ）のフォントサイズ** だけを参照します。

```scss
// ルート（html）が 16px の場合
html {
  font-size: 16px; // ブラウザ標準
}

.nav {
  font-size: 1.2rem; // 16px × 1.2 = 19.2px

  ul {
    font-size: 1.2rem; // どこまでネストしても 16px × 1.2 = 19.2px のまま！
  }
}
```

---

## 7-1. em と rem の違い（図解）

```
【em の場合：親要素を基準にするため雪だるま式に変化する】
<html> (16px)
  └── <body> (1.2em = 19.2px)
        └── <div class="card"> (1.2em = 23.04px)
              └── <p> (1.2em = 27.64px)  ← 意図せずどんどん巨大化！

【rem の場合：常に一番上の <html> だけを参照する】
<html> (16px)
  └── <body> (1.2rem = 19.2px)
        └── <div class="card"> (1.2rem = 19.2px)
              └── <p> (1.2rem = 19.2px)  ← 何重にネストしても常に同じ大きさ！
```

---

## 7-2. rem を使う絶大なメリット

1. **予測可能性が高い（PREDICTABLE）**：親要素のスタイルに左右されず、常にルート基準で一貫したサイズが保たれる。
2. **アクセシビリティに完全対応**：ブラウザの文字サイズ設定を変更した際、ルートのフォントサイズがスケールするため、サイト全体の文字と余白が美しく連動拡大する。
3. **ルート（`<html>`）を1箇所書き換えるだけで、サイト全体の拡大縮小が一瞬で可能**：
   たとえば「モバイルファーストで作り、PCやタブレットではデザイン全体（文字や余白）を一回り大きくしたい」という場合も、パーツごとにメディアクエリを何十箇所も書く必要がありません。

```scss
// 1. モバイル（基本）：ルートを 14px 相当にしておく
html {
  font-size: 14px; // 1rem = 14px
}

// 2. PC・タブレット（768px以上）：ルートを 16px に一括スケールアップ！
@media (width >= 768px) {
  html {
    font-size: 16px; // 1rem = 16px に拡大
  }
}

// 3. 各パーツ側では、画面幅ごとのスタイルを個別に書き直す必要がない
.card {
  padding: 1.5rem; // スマホ: 21px (14×1.5) → PC: 24px (16×1.5) に自動拡大！

  &__title {
    font-size: 1.25rem; // スマホ: 17.5px (14×1.25) → PC: 20px (16×1.25) に自動拡大！
  }
}
```

> [!TIP]
> 実務ではブラウザの文字サイズ設定（アクセシビリティ）を尊重するため、スマホ時は `html { font-size: 87.5%; }`（16px の 87.5% = 14px）、PC時は `html { font-size: 100%; }`（16px）のように `%` で指定するのがより推奨されます。

# 8. ビューポート単位（vw, vh, svh, dvh, lvh）

ブラウザの画面サイズ（Viewport）に直接連動する単位です。

- **`1vw`**：画面横幅の 1%（画面幅が 1200px なら 12px）
- **`1vh`**：画面高さの 1%（画面高が 800px なら 8px）

---

## 8-1. 【注意】`100vw` を使ってはいけない理由

画面いっぱいに広げたいときに `width: 100vw;` と書いてしまいがちですが、**これはNG** です。
なぜなら、`100vw` は **「ブラウザの垂直スクロールバーの幅を含んだ横幅」** を計算してしまうためです。
ページが縦長でスクロールバーが出ている場合、`100vw` を指定した要素は画面外にはみ出し、**下部に不要な横スクロールバー（横揺れバグ）が発生** します。

```scss
// ❌ 悪い例：横スクロールバーが発生する危険大
.hero {
  width: 100vw;
}

// ⭕️ 正しい例：スクロールバーを除いたコンテンツ幅いっぱいに広がる
.hero {
  width: 100%;
}
```

---

## 8-2. スマホの「100vh問題」とモダンな解決策（`dvh`, `svh`, `lvh`）

スマートフォン（iOS Safari や Android Chrome）では、画面をスクロールするとアドレスバーやツールバーが出現したり隠れたりします。
従来の `100vh` はアドレスバーが隠れた状態の最大高さを基準にしていたため、**「スマホで見ると最下部のボタンがアドレスバーに隠れて押せない！」** という深刻な問題がありました。

これを解決するために新しく導入されたのが以下の3つの単位です：

| 単位 | 正式名称 | 特徴 |
|:---:|:---:|---|
| **`svh`** | Small Viewport Height | アドレスバーが **表示されている状態** の最も小さい画面高さを基準にする |
| **`lvh`** | Large Viewport Height | アドレスバーが **隠れた状態** の最も大きい画面高さを基準にする |
| **`dvh`** | Dynamic Viewport Height | アドレスバーの出し入れに合わせて **リアルタイムに可変する** 画面高さを基準にする |

```scss
// スマホで綺麗にファーストビューを全画面表示したい場合
.mainvisual {
  height: 100vh; // 古いブラウザ用のフォールバック
  height: 100dvh; // アドレスバーの伸縮にリアルタイムに追従する最新指定！
}
```

# 9. ルートフォントサイズの設計戦略

`rem` の良さは理解できても、1つ大きな疑問が湧きます。
**「デザインカンプが px で作られているのに、いちいち 16 で割り算して rem を計算するのは面倒じゃないか？」** という点です。

例えば、デザインカンプで文字サイズが `28px` だった場合：
`28 ÷ 16 = 1.75rem` と電卓を叩く必要があります。

この計算の手間を解消するために、現場では主に **2つのアプローチ** が使われてきました。

---

## 9-1. アプローチA：「html { font-size: 62.5%; }」手法（古典的ハック）

Web制作の歴史の中で、古くから広く使われてきた有名なテクニックが **「62.5% 指定」** です。

```css
html {
  font-size: 62.5%; /* 16px × 62.5% = 10px になる！ */
}

body {
  font-size: 1.6rem; /* 10px × 1.6 = 16px（基準に戻す） */
}

h1 {
  font-size: 2.8rem; /* 10px × 2.8 = 28px（電卓不要！小数点をずらすだけ） */
}

p {
  font-size: 1.4rem; /* 10px × 1.4 = 14px */
}
```

### なぜ 62.5% なのか？
ブラウザのデフォルト文字サイズは通常 `16px` です。
`16px × 0.625 = 10px` となり、**ルート要素が「10px」相当** になります。
すると、`24px → 2.4rem`、`32px → 3.2rem` のように、**カンプの数値を10で割る（小数点を左に1つ移動する）だけで暗算できる** ようになります。

### 【注意】62.5% 指定のデメリット
一見便利に見えるこの手法ですが、現代の制作では以下のデメリットがあり、採用が見送られるケースが増えています：

1. **外部コンポーネントとの衝突**：BootstrapやTailwind CSS、WordPressプラグインなどのサードパーティ製ライブラリを読み込んだ際、ライブラリ側は「ルート=16px」を前提に作られているため、デザインが極端に縮小して崩れる。
2. **直感的でないCSS**：`font-size: 62.5%` という謎の数値をCSSの先頭に必ず置く必要があり、初見の開発者が混乱する。

---

## 9-2. アプローチB：Sass関数 `@function rem($px)` によるモダンな解法（★推奨）

Sassを使える環境であれば、`html` に不自然なハックを加える必要はありません。
**「`html` は標準の 16px（100%）のままにしておき、Sassの関数で px を rem に自動変換させる」** のが最も美しく安全なアプローチです。

### 【理解を深める】`@mixin` と `@function` の違いとは？

前回学習した `@mixin` と、今回登場する `@function`。どちらも「処理を共通化・再利用するもの」ですが、**目的と出力結果が根本的に異なります**。

| 項目 | `@mixin`（ミキシン） | `@function`（関数 / ファンクション） |
|---|---|---|
| **主な目的** | スタイルの**「塊（複数行のCSS宣言）」**を出力する | 計算された**「単一の値（数値・色・文字列）」**を返す |
| **呼び出し方** | **`@include`** を使って独立した行で呼び出す | プロパティの **値の部分** に直接書く |
| **出力結果** | `width: ...; margin: ...;` などのCSSルール | `1.5rem` や `3vw` などの「値」だけ |
| **終了命令** | スタイルブロックを展開して終了 | **`@return`** で必ず計算結果の値を返す |

```scss
// 1. @mixin の例：スタイルの「塊（レシピ）」を差し込む
@mixin inner($mw: 1200px) {
  max-width: $mw;
  margin-inline: auto;
  width: 88%;
}

.container {
  @include inner(); // ← 複数行のCSSプロパティがそのまま展開される！
}

// 2. @function の例：「電卓」として計算結果の単一の値を返す
@function rem($px) {
  @return #{math.div($px, 16)}rem; // ← @return で計算結果の値を返す！
}

.heading {
  font-size: rem(24); // ← プロパティの値（1.5rem）として埋め込まれる！
}
```

> **覚え方のコツ**：
> - **`@mixin` は「スタンプ」**：決まったスタイルのセットをペタッと貼る。
> - **`@function` は「電卓」**：数値を渡すと計算して結果の数値をポンと返す。

---

### 実務で大活躍する Sass 関数セット（自作関数の活用例）

`rem()` のほかにも、電卓で計算するのが面倒な数値を `@function` に任せるとコーディング効率が劇的に上がります。

```scss
@use "sass:math";

// 基準となるルートフォントサイズ（ブラウザ標準）
$font-size-base: 16;

// ① pxをremに変換する関数
@function rem($px-value) {
  @return #{math.div($px-value, $font-size-base)}rem;
}

// ② XD/Figmaのトラッキング値をemに変換する関数
@function ls($xd-value) {
  @return #{math.div($xd-value, 1000)}em;
}

// ③ 【別の活用例】カンプのpxを画面幅に対する「vw」に自動変換する関数
// （例: 1200pxカンプで36pxの文字 → 36 ÷ 1200 × 100 = 3vw）
@function vw($px-value, $base-width: 1200) {
  @return #{math.div($px-value, $base-width) * 100}vw;
}

// ④ 【別の活用例】親要素の幅に対する「%」を自動計算する関数
// （例: 1200pxの親幅の中で400pxのカラム → 400 ÷ 1200 = 0.3333... → 33.3333333333%）
@function pct($target-px, $parent-px) {
  // ※従来の percentage() でも動作しますが、モダンなDart Sassでは非推奨の警告が出るため、
  //   @use "sass:math"; を読み込んで「math.percentage()」と書くのが最新の標準ルールです！
  @return math.percentage(math.div($target-px, $parent-px));
}
```

> [!NOTE]
> **【補足】`percentage()` と `math.percentage()` について**  
> Sassには数値をパーセントに変換する組み込み関数 `percentage()` があります。従来のSassでは単体で使われていましたが、最新の Dart Sass ではグローバル関数の廃止が進んでおり、警告（Deprecation Warning）が出ます。そのため、現在は `math.div()` と同様に `@use "sass:math";` を読み込み、**`math.percentage()`** と書くのが最新のベストプラクティスです。

### 実際のコーディングでの使い方

```scss
body {
  font-size: rem(14); // → 0.875rem にコンパイル！
  letter-spacing: ls(50); // → 0.05em にコンパイル！
}

.hero__title {
  // clamp の推奨値も vw() 関数を使えば暗算不要！
  font-size: clamp(rem(24), vw(36), rem(36)); // → clamp(1.5rem, 3vw, 2.25rem) に自動変換！
  margin-bottom: rem(24); // → 1.5rem にコンパイル！
}

.column {
  // 1200pxのインナー内で400pxの幅を%で指定したい場合
  width: pct(400, 1200); // → 33.3333333333% に自動変換！
}
```

```css
/* コンパイル後の CSS */
body {
  font-size: 0.875rem;
  letter-spacing: 0.05em;
}

.hero__title {
  font-size: clamp(1.5rem, 3vw, 2.25rem);
  margin-bottom: 1.5rem;
}

.column {
  width: 33.3333333333%;
}
```

電卓を叩く必要は一切なく、**「カンプのpx数値をそのまま `rem(28)` と書くだけ」** で、ブラウザには正しい `rem` が出力されます。
外部ライブラリとも一切衝突せず、アクセシビリティも100%担保されます。

# 10. 余白設計と8pxグリッド

`rem()` 関数を使えば自由自在にpxからremへ変換できますが、ここでもう一つ実務上の重要な問題が発生します。
デザインカンプを測ったときに、余白が **`18px`**, **`21px`**, **`23px`**, **`25px`** のようにバラバラだった経験はありませんか？

このように場当たり的な数値（マジックナンバー）をそのまま `rem(21);` や `rem(23);` と打ち込んでいると、以下の問題が生じます：

1. **デザインのリズム（一貫性）が崩れる**：パーツごとに微妙に余白が異なり、全体として素人くさい印象になる。
2. **迷いが生じて制作スピードが落ちる**：「ここは21px、あそこは23px…」と毎回カンプを厳密に測ることに追われてしまう。

---

## 10-1. 8pxグリッドの考え方

Webデザインのスタンダードでは、**「4px または 8px の倍数」** で余白を統一する「8pxグリッドシステム」が広く採用されています。

画面全体の余白（`padding`, `margin`）やパーツのサイズを 8px の倍数で統一することで、画面全体に心地よいリズムと統一感が生まれます。

| 目安 | px値 | rem表記 | 主な用途の目安 |
|---|---|---|---|
| **極小** | 4px | `rem(4)` | アイコンと文字の隙間、タグの内側など（半歩分） |
| **小** | 8px | `rem(8)` | ボタンの上下余白、バッジ、行間の調整 |
| **中** | 16px | `rem(16)` | コンポーネント内の基本余白、要素間の標準マージン |
| **大** | 24px | `rem(24)` | 見出しと本文の間、カード内の広めの余白 |
| **特大** | 32px | `rem(32)` | カード同士の間隔、大きめのコンポーネント間 |
| **巨大** | 40px〜48px | `rem(40)`, `rem(48)` | セクション内の大きな区切り |
| **セクション間** | 80px〜120px | `rem(80)`, `rem(120)` | セクションとセクションの上下区切り |

---

## 10-2. 実装：すべて `rem()` 関数で直感的に記述する

余白を管理するためにわざわざ専用の変数をたくさん作らなくても、**「8の倍数を意識しながら、すべて `rem()` 関数で書く」** だけで、美しい余白設計とアクセシビリティ（rem化）が同時に達成できます。

```scss
.card {
  // 上下32px、左右24pxの余白
  padding: rem(32) rem(24);
  // 角丸も 8px
  border-radius: rem(8);

  &__title {
    // 見出し下の余白 16px
    margin-bottom: rem(16);
  }

  &__tag {
    // タグ間の隙間 4px
    margin-right: rem(4);
  }
}
```

カンプの数値をそのまま `rem(16)` や `rem(24)` と記述できるため、変数名を覚える手間がなく、コードの可読性も抜群です。

<aside>
💡

**カンプで 23px のような中途半端な数値が出てきたら？**

デザインカンプを測ったときに `23px` や `15px` のような半端な数値がある場合、デザイナーの「意図しない1pxのズレ（制作ミス）」であることがよくあります。
実務では「近い8の倍数（24px や 16px）に寄せる」か、デザイナーに確認するのが一般的です。
どうしてもその数値が必要な場合も、そのまま `rem(23)` と書くだけで柔軟に対応できます。

</aside>

# 11. 流体タイポグラフィ（Fluid Typography）と `clamp()`

これまでのレスポンシブは、「スマホ用の文字サイズ」と「PC用の文字サイズ」をメディアクエリ（ブレイクポイント）でカクッと切り替えるのが主流でした。
しかし、これでは **「スマホとPCの中間サイズ（タブレット等）」で文字が不自然に大きすぎたり小さすぎたりする問題** が起こります。

これを解決するのが、CSSの比較関数 **`clamp()`** を使った **「流体タイポグラフィ（Fluid Typography）」** です。

---

## 11-1. `clamp()` の基本構文

```css
font-size: clamp(最小値, 推奨値, 最大値);
```

- **最小値（下限ガード）**：どれだけ画面が小さくなっても、これ以上小さくならない下限サイズ（スマホ表示時のサイズ）。
- **推奨値（可変値）**：画面幅に応じてスムーズに伸縮する相対値（通常 `vw` を使用）。
- **最大値（上限ガード）**：どれだけ画面が巨大になっても、これ以上大きくならない上限サイズ（PC表示時のサイズ）。

---

## 11-2. サンプルデータ（h2）を例に計算してみよう

今回の授業演習データ `06-Roysha-rem` のセクション見出し（`h2.intro__title`）では、次のように `clamp()` を指定しています。

```scss
// サンプルデータ（Roysha）の見出し
.intro__title {
  font-size: clamp(rem(24), 3vw, rem(36));
}
```

- **最小値**：`rem(24)`（スマホ時の最小値：24px）
- **最大値**：`rem(36)`（PC時の最大値：36px）
- **推奨値**：`3vw`（画面幅に応じて伸び縮みするサイズ）

### 推奨値（3vw）はどうやって計算するのか？

「最小値（24px）と最大値（36px）はデザインカンプを見ればすぐわかるけれど、**真ん中の推奨値（〇vw）はどうやって計算するの？**」と疑問に思うはずです。

実務では、推奨値の `vw` は **「デザイン全体のコンテンツ幅（inner の `max-width: 1200px` など）」を基準に逆算** して決定します。

#### 【vw の計算公式】
```
推奨値(vw) = 目標文字サイズ(px) ÷ 基準とする画面幅(px) × 100
```

今回の Roysha（PC目標文字サイズ: 36px / インナー最大幅: 1200px）で計算してみると：

```
36px ÷ 1200px × 100 = 3vw
```

端数が出ず、綺麗に **`3vw`** と割り切れます！
このように、**「コンテンツ幅が最大の 1200px に達したとき、ちょうど最大値の 36px になるような vw」** を推奨値に設定しています。

### 画面幅による挙動シミュレーション

`clamp(rem(24), 3vw, rem(36))` を指定した場合、画面幅に応じてブラウザが自動的に以下のように切り替えます。

| 画面幅（Viewport） | 推奨値（`3vw`）の計算値 | 実際に適用される文字サイズ | 状態 |
|---|---|---|---|
| **375px**（スマホ） | `375px × 0.03 = 11.25px` | **24px**（`rem(24)`） | 最小値ガードが発動（小さすぎて読めなくなる事故を防ぐ） |
| **800px**（タブレット） | `800px × 0.03 = 24px` | **24px** | ここから可変がスタート！ |
| **1000px**（小型ノートPC） | `1000px × 0.03 = 30px` | **30px** | **推奨値（3vw）がそのまま滑らかに適用！** |
| **1200px**（インナー最大幅） | `1200px × 0.03 = 36px` | **36px** | ここで最大値に到達！ |
| **1440px**（大画面デスクトップ） | `1440px × 0.03 = 43.2px` | **36px**（`rem(36)`） | 最大値ガードが発動（巨大化して画面を崩すのを防ぐ） |

**ポイント**：
1. **スマホ（〜800px）**：最小値の **24px** をしっかりキープ。
2. **タブレット〜PC（800px〜1200px）**：ブレイクポイントによるカクつきが一切なく、**24px 〜 36px の間を無段階で滑らかに伸縮**。
3. **大画面（1200px〜）**：最大値の **36px** でピタッと止まり、デザインが崩れない。

<aside>
💡

**メディアクエリを書かずにレスポンシブが完結する！**

`clamp()` を使うと、たった1行のコードで「スマホ〜タブレット〜PC」の全画面サイズに完璧に適応します。
メディアクエリを何行も書いて上書きする必要がなくなるため、コードが劇的にスリムになります。
文字サイズだけでなく、`padding: clamp(rem(20), 4vw, rem(60));` のようにセクションの余白調整にも絶大な威力を発揮します。

</aside>

# 12. 実務チートシート：プロパティ別の単位選定基準

「結局、どのプロパティにどの単位を使えばいいの？」と迷ったときは、以下の実務基準に従ってください。

| プロパティ | 推奨単位 | 理由・選定の根拠 |
|---|:---:|---|
| **`font-size`** | **`rem`**<br>（または `clamp()`） | アクセシビリティ（ブラウザの文字サイズ変更）に対応するため。カスケード事故を防ぐ。大見出しは `clamp()` で流体化。 |
| **`line-height`** | **単位なし数値**<br>（例: `1.7`） | 単位なしの倍率で指定すると、フォントサイズ変更時に常に適切な行間比率が子要素にも正しく継承される（`px` や `%` はNG）。 |
| **`letter-spacing`** | **`em`**<br>（例: `0.05em`） | カンプのトラッキング値を変換。フォントサイズが変わっても同じ字間比率を維持できる。 |
| **`width` / `max-width`** | **`%`** / **`rem`** / **`px`** | コンテナ幅は `%` や `rem`。文字数に連動させたいラベルやボタンは `em`。 |
| **`height`** | **指定しない**<br>（または `dvh` / `aspect-ratio`） | 高さは中身のテキスト量に応じて成り行き（`auto`）にするのが基本。全画面表示のみ `100dvh` を使用。 |
| **`margin` / `padding`** | **`rem`**<br>（`rem()` 関数） | ルートの文字サイズと連動して余白もスケーリングさせる（8の倍数を基準にする）。ボタンのプロポーション連動のみ `em` を使用。 |
| **`border-width`** | **`px`**<br>（例: `1px`, `2px`） | 境界線は画面サイズによって太くしたくないため、固定の絶対値（`px`）で指定するのが自然。 |
| **`border-radius`** | **`rem`** / **`px`** / **`9999px`** | 角丸を文字サイズに追従させたい場合は `rem`。完全なカプセル型ボタンは `9999px`（または `50vh`）。 |

## 13-1. 授業内演習：Roysha の rem & 相対単位リファクタリング

授業では、第2回で組んだサンプルデータ（`02-roysha-bem`）をベースに、px で固定されていたコードを **Sass ＋ 相対単位（rem, em, clamp）**（`06-Roysha-rem`）にリファクタリング（再構築）していきます。

### 主な実装ステップ

1. **Sass関数と変数の準備**：`sass/style.scss` の冒頭で `@use "sass:math";` を読み込み、`rem()` 関数や `ls()` 関数、カラー変数、`@mixin inner()` を定義する。
2. **文字サイズと字間の置換**：
   - 本文の `font-size: 16px;` を `rem(16)` に、見出しやキャッチコピーを `rem()` に置換する。
   - `letter-spacing` を `ls(50)` などのem関数に置き換える。
3. **メイン見出しの流体化（clamp）**：
   - `.intro__title` の文字サイズを `clamp(rem(24), 3vw, rem(36))` に置き換え、画面幅に応じた流体タイポグラフィを適用する。
4. **ボタンのプロポーション連動（em）**：
   - `.btn` の内側余白を `padding: 1.25em 0;` に置き換え、文字サイズに連動して余白が伸縮する構造にする。
5. **余白と角丸の rem 化**：
   - 余白（`padding`, `margin`）や角丸（`border-radius`）の px を `rem()` 関数に置き換える（8pxの倍数を意識する）。
6. **ブラウザの文字サイズ変更テスト**：
   - Chromeのフォントサイズを「極大」に変更し、レイアウトが崩れずに文字と余白が美しく拡大されることを確認する。
